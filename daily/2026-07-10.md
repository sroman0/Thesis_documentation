# 2026-07-10 - Piano logging strutturato con zap

## Obiettivo

La prossima fase riguarda il logging applicativo del tool. Il punto da
correggere non e' la raccolta eventi, ma il modo in cui il runtime comunica
stato, errori e diagnostica.

Oggi il progetto contiene ancora messaggi manuali basati su `fmt.Printf`,
`fmt.Fprintf(os.Stderr, ...)` o stampe ad hoc. Funzionano per il debug rapido,
ma non scalano bene quando il runtime include policy, detector, alert e molti
hook eBPF.

## Decisione

Il logging runtime verra' migrato a `go.uber.org/zap`.

La scelta e' motivata da tre esigenze:

- avere livelli coerenti (`error`, `warn`, `info`, `debug`);
- produrre log strutturati e filtrabili;
- evitare formattazioni inutili nella hot path degli eventi.

La separazione corretta e':

```text
runtime logs  -> zap logger
raw events    -> pkg/output event printer
alerts        -> pkg/output alert printer
```

Quindi un evento `security_file_open` o un alert detector non deve diventare un
log applicativo. Sono output del prodotto. Il logger deve invece descrivere
cosa sta facendo il runtime: startup, config, attach probe, policy caricate,
detector caricati, errori e diagnostica.

## Implementazione Fase 1

La prima fase e' stata implementata con:

```text
demo_project/pkg/logging/logger.go
demo_project/pkg/logging/logger_test.go
```

`logger.go` espone:

```go
type Config struct {
    Level  string
    Format string
}

func New(cfg Config) (*zap.Logger, error)
```

Il costruttore:

- traduce `debug|info|warn|error` nei livelli zap;
- usa `info` come default;
- usa formato `console` come default;
- accetta anche formato `json` per evoluzioni future;
- scrive i log su `stderr`;
- rifiuta livelli e formati non supportati.

`logger_test.go` verifica livelli validi, default, formato JSON e casi di
errore.

Verifica eseguita:

```bash
GOCACHE=/tmp/go-build go test ./pkg/logging
```

Risultato:

```text
ok github.com/V3suv1us/demo_project/pkg/logging
```

Il piano completo resta documentato in
[Piano logging strutturato con zap](../next-steps/zap-logging-plan.md).

## Impatto atteso

Questa fase non deve modificare:

- eventi emessi dal kernel;
- decoder;
- policy matching;
- detector engine;
- alert output.

Serve invece a rendere piu' controllabile il runtime. In particolare:

- `--log-level error` dovra' ridurre il rumore operativo;
- `--log-level info` dovra' mostrare solo lifecycle essenziale;
- `--log-level debug` dovra' mostrare dettagli di attach, drop reason e debug
  detector.

## Prestazioni

Il target operativo resta sotto circa il 5% di un core nelle run normali.
Per questo motivo i log nella hot path devono essere minimali e disabilitabili.

Regola pratica: niente `fmt.Sprintf` per costruire messaggi debug dentro il
percorso evento. I campi devono essere passati come campi zap tipizzati.

`cfg.LogLevel`, usa zap per i log di lifecycle del layer applicativo, esegue

La Fase 4 e la diagnostica debug interna sono state completate in
`demo_project/pkg/ebpf/project.go`.

Sono stati migrati a zap:

- `attached probes`;
- `attached probe`;
- `received first raw event`;
- `decoded first event`;
- `drop event`;
- `perf buffer lost events`;
- `decode event`;
- `print event`;
- `detector error`;
- `print alert`.

Gli eventi raw e gli alert continuano a passare dai printer. La migrazione
riguarda solo i log diagnostici del runtime.

Anche il callback libbpf e' stato collegato a zap. I messaggi CO-RE/libbpf
restano filtrati da `--log-level`, ma ora passano dallo stesso sink strutturato
del runtime. Per distinguerli dai log applicativi vengono aggiunti i campi:

```text
source=libbpf
libbpf_level=<livello numerico libbpf>
```

E' stata inoltre aggiunta la flag:

```text
--log-format console|json
```

Questa flag controlla solo i log runtime. Non modifica il formato degli eventi
o degli alert, che restano gestiti da `--output` e `--alerts-output`.

La motivazione principale e' l'esecuzione futura in container/pod Kubernetes:
in quel contesto e' utile produrre log runtime in JSON senza cambiare il
formato operativo degli eventi.

E' stata rimossa anche la stampa manuale iniziale da `cmd/project/cmd/root.go`.
Quel messaggio era un log runtime su `stdout`; ora viene prodotto dal runner
tramite zap su `stderr`, mantenendo `stdout` piu' pulito per eventi e alert.

## Implementazione `--alerts-only`

E' stata aggiunta la modalita' `--alerts-only`.

Comportamento:

- abilita automaticamente l'output alert;
- sopprime la stampa degli eventi raw;
- non elimina gli eventi dalla pipeline;
- policy e detector continuano a ricevere gli eventi decodificati.

Questa modalita' serve soprattutto per demo e test detector, dove l'obiettivo e'
osservare il risultato della detection senza essere sommersi da righe
`event=...`.

Il test manuale ha confermato che `--alerts-only` sopprime correttamente gli
eventi raw. E' stato poi migliorato il formato table degli alert: ogni riga
inizia con `type=alert` e include il primo evento sorgente tramite
`source_event`, `source_pid`, `source_uid`, `source_comm` e `source_args`.
Questo rende l'output piu' utile durante una demo, perche' mostra direttamente
quale evento ha fatto scattare il detector.

Esempio:

```bash
sudo ./dist/project \
  --policy rules/policies/demo-detectors.yaml \
  --detectors rules/detectors \
  --alerts-only \
  --alerts-output table \
  --output table \
  --log-level error
```

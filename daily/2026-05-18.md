## Workflow Docker introdotto

Il nuovo workflow e' pensato per standardizzare l'ambiente userspace di build.

```bash
make docker-image
make docker-build
make docker-shell
make docker-run ARGS="--events sched_process_exec --output table"
```

La build avviene in container, ma gli artefatti restano nella directory locale:

```text
demo_project/dist/project.bpf.o
demo_project/dist/project
```

L'esecuzione eBPF resta invece legata al kernel host. Per questo `docker-run`
usa:

```text
--privileged
--pid=host
/sys/kernel/btf
/sys/fs/bpf
```

Docker non cambia il kernel della VM: rende piu' prevedibile l'ambiente di
compilazione, ma i limiti di verifier, helper e BTF restano quelli del kernel
Rocky/RHEL usato come host.

## Problemi emersi

Durante `make docker-image`, `apt-get update` falliva con:

```text
Temporary failure resolving 'deb.debian.org'
```

Il problema non era nel Dockerfile, ma nella risoluzione DNS dentro il container
di build. La soluzione pratica e' stata usare:

```bash
docker build --network=host
```

Durante `make docker-run`, la fase `docker-build` ha poi fallito durante il
download dei moduli Go:

```text
lookup proxy.golang.org: i/o timeout
```

Per questo anche il container usato da `docker-build` e `docker-shell` usa ora
host networking.

Un secondo dettaglio emerso riguarda i path assoluti. La build `libbpf` genera
file `pkg-config` con path assoluti. Se il repository viene montato dentro il
container in un path diverso, per esempio `/src`, quei path possono non
esistere. Il Makefile monta quindi il repository nello stesso path assoluto
dell'host.

## Decisioni tecniche

- Docker viene introdotto come supporto alla build e allo sviluppo, non come
  isolamento completo del runtime eBPF.
- Il runtime Docker resta privilegiato, perche' deve caricare programmi eBPF
  nel kernel host.
- Il workflow locale `make build` resta valido e piu' rapido sulla VM gia'
  configurata.
- Il workflow Docker diventa utile per demo, riallineamento ambienti e
  collaborazione tra branch.

## Stato demo

Il progetto e' arrivato a una prima versione dimostrabile:

- build eBPF/Go funzionante tramite Makefile;
- runtime basato su `libbpfgo`;
- reader duale ring buffer/perf buffer;
- selezione eventi con `--events` e `--drop-events`;
- filtro `--comms`;
- output `table` e `json`;
- hook process, security e networking disponibili;
- workflow Docker documentato.

Questa milestone e' adatta per un tag GitHub di tipo demo, per esempio:

```text
v0.1.0-demo
```

# 2026-05-05 - Selezione eventi e probe registry Tracee-light

## Obiettivo

Ridurre il rumore dell'output runtime e avvicinare il progetto al modello di Tracee, introducendo una selezione esplicita degli eventi da abilitare.

Il problema pratico era evidente con `cap_capable`: il programma produceva molte righe JSON ravvicinate, spesso difficili da leggere durante i test manuali.

## Implementazione

E' stata aggiunta una configurazione runtime dedicata:

- `Config.Events.Include`;
- `Config.Events.Exclude`.

Le opzioni sono esposte tramite CLI:

```bash
sudo go run ./cmd/project --bpf-object pkg/ebpf/c/project.bpf.o --events sched_process_exec
sudo go run ./cmd/project --bpf-object pkg/ebpf/c/project.bpf.o --drop-events cap_capable
```

La lista dei programmi da attaccare e' stata spostata in `pkg/ebpf/probes/probes.go`.
Ogni entry collega:

- nome evento decodificato;
- nome programma eBPF;
- hook kernel;
- tipo di probe (`raw tracepoint` o `kprobe`).

`Project.New()` valida la selezione eventi e prepara la lista dei probe da attaccare.
`Project.Init()` attacca solo i probe selezionati.
`Project.Run()` mantiene anche un filtro userspace sugli eventi decodificati, utile come controllo difensivo.

E' stato poi introdotto `pkg/output`, un layer separato per la stampa degli
eventi decodificati. Il runtime eBPF non chiama piu' direttamente
`json.Marshal`, ma delega a un `Printer`.

Formati disponibili:

- `json`: output JSON line-oriented, utile per parsing automatico, con record
  normalizzato;
- `table`: output compatto per debug manuale da terminale.

Il JSON non serializza piu' direttamente `bufferdecoder.Event`: `event.go`
costruisce una vista con blocchi `process`, `host`, `kernel` e `args`.
`comm` e `uts_name` sono convertiti da array `[16]byte` a stringhe, e
l'argomento `cap` viene arricchito con label simboliche come
`CAP_SYS_ADMIN`.

## Differenza rispetto a Tracee

Tracee gestisce questa parte con componenti piu' ricchi: definizioni evento, probe group, policy, dipendenze e pipeline. Per l'MVP e' stato scelto un registry statico per tre motivi:

- e' coerente con l'attach esplicito gia' presente nel progetto;
- riduce il rischio su Rocky Linux 4.18;
- permette di controllare subito il rumore generato da hook ad alta frequenza.

Questa e' quindi una scelta Tracee-inspired, non una copia completa della sua architettura.

## Verifiche

Sono stati aggiunti test unitari in `pkg/ebpf/probes/probes_test.go` per:

- selezione di default di tutti gli eventi supportati;
- combinazione `include` + `exclude`;
- rifiuto di eventi non supportati;
- rifiuto di una selezione finale vuota.

Sono stati aggiunti test in `pkg/output` per:

- validita' del JSON prodotto;
- conversione di `comm` in stringa;
- mapping capability `21` -> `CAP_SYS_ADMIN`;
- rifiuto di formati output non supportati;
- contenuto essenziale dell'output table.

Comandi eseguiti:

```bash
GOCACHE=/tmp/go-build go test ./...
go run ./cmd/project --help
```

## Prossimo passo consigliato

Arricchire ulteriormente l'output senza perdere il formato JSON machine-readable:

- mappare syscall numeriche a nomi;
- mappare resource limit e opzioni `prctl`;
- aggiungere eventuali campi derivati utili per detection.

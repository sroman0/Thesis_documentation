# 2026-06-18 - Kernel tampering e superfici procfs/kprobe

## Obiettivo

La giornata e' stata dedicata ad ampliare la copertura sugli eventi di
hardening kernel, con focus su comportamenti tipici di moduli e codice kernel
che possono essere interessanti anche in scenari di rootkit o tampering.

## Cosa e' stato aggiunto

Sono stati implementati tre nuovi eventi:

- `proc_create`: osserva la creazione di entry procfs e salva il nome della
  entry insieme al puntatore `proc_ops`;
- `register_kprobe`: osserva la registrazione dinamica di kprobe e, tramite
  kretprobe, aggiunge anche il valore di ritorno;
- `kallsyms_lookup_name`: osserva lookup runtime di simboli kernel e salva il
  simbolo richiesto con l'indirizzo restituito.

Per ogni evento sono stati aggiornati:

- ID evento e definizioni Go;
- specifiche degli argomenti;
- registry probe;
- programma eBPF;
- mapping di output per puntatori e return value;
- documentazione operativa.

## Decisioni tecniche

`register_kprobe` e `kallsyms_lookup_name` usano una coppia entry/return perche'
il valore finale e' disponibile solo al ritorno della funzione kernel. Questo
permette di tenere l'evento piu' utile senza dover stampare soltanto la
richiesta iniziale.

`proc_create` resta invece un kprobe diretto e compatto: per ora mostra il nome
della entry e l'indirizzo della struttura operazioni, evitando di copiare
strutture piu' complesse che aumenterebbero il costo del verifier.

Il layer di output e' stato corretto per mostrare indirizzi kernel e callback in
esadecimale anche quando arrivano come valori `uint64` alti.

## Verifica

Comandi eseguiti:

```bash
make bpf
go test ./...
make build
./dist/project --list-events | rg "proc_create|register_kprobe|kallsyms_lookup_name"
```

E' stato anche fatto un test di attach runtime con:

```bash
sudo ./dist/project --events proc_create,register_kprobe,kallsyms_lookup_name --output table --log-level error
```

Durante il test e' stato osservato almeno un evento `register_kprobe`, generato
dalla registrazione di un kprobe su simboli kernel.

## Limiti noti

`kallsyms_lookup_name` non e' semplice da innescare da userspace con un comando
generico: serve codice kernel o un modulo che chiami realmente quella funzione.
Se il tracer parte ma non stampa eventi, significa che durante la finestra di
test non e' avvenuto alcun lookup.

Restano fuori, per una fase successiva, `bpf_attach`, superfici debugfs e logica
di hidden module detection.

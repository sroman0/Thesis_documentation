# 2026-07-14 - Dedup temporale degli alert detector

## Contesto

Dopo l'introduzione di policy, detector YAML e `--alerts-only`, il problema piu'
evidente era la leggibilita' dell'output. Anche con detector piu' stringenti,
alcuni processi possono generare lo stesso alert molte volte in pochi secondi.

Esempio tipico:

```text
sensitive-file-open -> stesso processo -> stesso pathname -> alert ripetuti
```

Questo comportamento non indica necessariamente un nuovo attacco a ogni riga:
spesso e' solo la stessa attivita' ripetuta rapidamente.

## Implementazione

In `demo_project/pkg/detectors/engine.go` e' stato aggiunto un dedup temporale
centrale nel detector engine.

La finestra di default e':

```text
5s
```

La chiave di dedup usa:

```text
detector_id
alert title
severity
source event name
pid
uid
comm
source event args
```

Questa scelta mantiene visibili alert diversi, ma sopprime duplicati immediati
dello stesso comportamento.

## Metriche

Le metriche del detector engine ora distinguono:

```text
AlertsEmitted
AlertsSuppressed
```

`AlertsSuppressed` permette di verificare che il dedup stia lavorando senza
confondere alert emessi e alert generati dai detector.

## Test

Sono stati aggiunti test in `demo_project/pkg/detectors/engine_test.go` per
verificare che:

- due alert identici nella stessa finestra producano un solo alert in output;
- dopo la finestra temporale lo stesso alert possa essere emesso di nuovo;
- le metriche distinguano alert emessi e alert soppressi.

Verifica eseguita:

```bash
GOCACHE=/tmp/go-build go test ./pkg/detectors/...
```

## Refinement anti-rumore dei detector demo

Dopo i test manuali, alcuni detector producevano alert tecnicamente corretti ma
troppo rumorosi per una demo. Il caso principale era `sudo`: durante una normale
esecuzione genera piu' cambi UID e comandi ausiliari come `unix_chkpwd`.

Sono stati quindi resi piu' stringenti i detector demo:

- `privileged-uid-change` guarda transizioni da utente non-root verso euid 0;
- `root-exec` esclude processi ausiliari come `sudo` e `unix_chkpwd`;
- `sensitive-file-open` evita alert su alcuni accessi operativi non utili alla
  demo;
- `privilege-exec-chain` e `privilege-sensitive-file-chain` mantengono solo le
  sequenze con segnale chiaro, per esempio `sudo cat /etc/passwd`.

Questa non e' una regola universale di detection: e' una taratura dei detector
demo per ridurre falsi positivi e mostrare meglio la differenza tra evento raw,
point alert e collective alert.

## MITRE negli alert

I metadati MITRE dichiarati nei detector YAML vengono ora propagati fino agli
alert.

Nel formato table il riferimento viene mostrato in forma compatta:

```text
mitre=TA0004|TA0007|T1548|T1083
```

Nel formato JSON il blocco resta strutturato come `threat`, cosi' un futuro
consumer puo' leggere tactic, technique, data source e data component senza
parsing testuale.

Il test manuale del detector `privilege-sensitive-file-chain` ha confermato il
flusso completo:

```text
security_task_fix_setuid -> security_file_open
```

con output:

```text
type=alert ... detector=privilege-sensitive-file-chain ... mitre=TA0004|TA0007|T1548|T1083 sequence=...
```

Limite rimasto: MITRE e' gia' presente nell'alert, ma non viene ancora usato
per selezionare automaticamente policy o detector. Questo resta un prossimo
step della roadmap.

## Come testare manualmente

Avviare il tool:

```bash
sudo ./dist/project \
  --policy rules/policies/demo-detectors.yaml \
  --detectors rules/detectors \
  --alerts-only \
  --alerts-output table \
  --log-level error
```

In un secondo terminale:

```bash
cat /etc/passwd
cat /etc/passwd
cat /etc/passwd
```

Output atteso: un solo alert `sensitive-file-open` nella finestra breve.

Dopo circa 5 secondi:

```bash
cat /etc/passwd
```

L'alert puo' essere emesso nuovamente.

## Impatto

Questa modifica non cambia gli hook eBPF e non cambia i detector YAML. Riduce
solo la ripetizione degli alert gia' prodotti dal layer detector.

E' un passo preparatorio per i detector collective: prima di correlare sequenze
di eventi, l'output degli alert singoli deve essere leggibile.

## Primo detector collective

Dopo il dedup e' stata aggiunta la prima forma MVP di detector collective nel
runtime YAML.

File principali:

```text
demo_project/pkg/detectors/yaml/detector.go
demo_project/pkg/detectors/yaml/parser.go
demo_project/rules/detectors/privilege_exec_chain.yaml
```

Il detector YAML ora puo' gestire sequenze ordinate corte quando:

```yaml
stateful: true
steps:
  - event: ...
  - event: ...
```

La prima sequenza implementata e':

```text
security_task_fix_setuid(new_euid=0)
  -> sched_process_exec(uid=0)
```

entro una finestra di 5 secondi.

Il nuovo detector demo e':

```text
privilege-exec-chain
```

Genera un alert high quando una transizione privilegiata e' seguita da una
esecuzione come root.

## Output degli alert collective

Dopo il primo test manuale del detector `privilege-exec-chain`, l'alert
mostrava correttamente `events=2`, ma la riga table esponeva solo gli argomenti
del primo evento tramite `source_args`.

Per rendere piu' leggibile la catena, `demo_project/pkg/output/alert.go` ora
aggiunge il campo `sequence` quando un alert contiene piu' eventi correlati:

```text
sequence=security_task_fix_setuid(...)->sched_process_exec(...)
```

Questa modifica e' volutamente confinata al layer output: il detector continua a
emettere un `detectors.Alert` con l'array completo di eventi correlati, mentre il
printer table decide come sintetizzarli per una demo da terminale. Il formato
JSON conserva gli eventi come array strutturato.

La stringa `sequence` ha una lunghezza massima per evitare output troppo lunghi
quando gli argomenti contengono path estesi.

Dopo il test manuale, il formato table e' stato ulteriormente pulito: per alert
collective non vengono piu' stampati i campi `source_*`, perche' duplicavano il
primo elemento gia' incluso in `sequence`. Gli alert point continuano invece a
usare `source_event`, `source_pid`, `source_uid`, `source_comm` e `source_args`.

## Policy preset

Lo step 21 della roadmap policy/detector e' stato consolidato aggiungendo nuove
policy YAML dedicate sotto `demo_project/rules/policies`:

```text
collective-privilege-exec.yaml
point-process-security.yaml
sensitive-file-access.yaml
kernel-module-activity.yaml
full-demo.yaml
```

`demo-detectors.yaml` resta disponibile come policy compatibile con i primi
test. I nuovi file separano gli scenari:

- `collective-privilege-exec.yaml`: solo eventi necessari al detector
  `privilege-exec-chain`;
- `point-process-security.yaml`: root execution e transizioni UID;
- `sensitive-file-access.yaml`: apertura di file sensibili;
- `kernel-module-activity.yaml`: inizializzazione moduli kernel;
- `full-demo.yaml`: tutti i detector demo correnti.

Questa scelta rende i comandi piu' leggibili e riduce ambiguita' durante le
demo: invece di selezionare manualmente eventi con `--events`, si usa una policy
dedicata allo scenario da mostrare.

## Benchmark userspace

E' stato aggiunto un primo benchmark userspace ripetibile:

```text
demo_project/scripts/benchmark_userspace.sh
```

Il Makefile espone il target:

```bash
make benchmark-userspace
```

Lo script cerca il processo piu' recente chiamato `project`, legge i tick CPU da
`/proc/<pid>/stat` e calcola la CPU come percentuale di un singolo core. La
soglia default e' `5.0%`:

```bash
DURATION_SECONDS=120 CPU_THRESHOLD=5.0 make benchmark-userspace
```

Il comando stampa campioni periodici con CPU, RSS e numero thread, poi produce
una summary con media CPU, picco CPU, RSS massimo e thread massimi. Se la media
supera la soglia, lo script esce con codice `2`.

Questa prima fase misura il processo Go userspace. La componente eBPF
kernel-side resta da automatizzare con snapshot `bpftool` su `run_time_ns` e
`run_cnt`.

## Primo risultato benchmark

E' stato eseguito un benchmark userspace di 120 secondi sul profilo collective:

```bash
sudo ./dist/project \
  --events security_task_fix_setuid,sched_process_exec \
  --policy rules/policies/demo-detectors.yaml \
  --detectors rules/detectors/privilege_exec_chain.yaml \
  --alerts-only \
  --alerts-output table \
  --log-level error
```

Risultato osservato:

- CPU spesso tra `5.9%` e `7.7%`;
- picco massimo osservato `16.92%`;
- RSS stabilizzato intorno a `45 MiB`;
- thread `8-9`.

La summary finale non e' stata acquisita, quindi il dato resta parziale. Pero'
il comportamento e' sufficiente per indicare che questo profilo non rispetta
ancora stabilmente il target `<5%` di un core.

Priorita' di ottimizzazione:

1. ridurre eventi processati in userspace prima possibile;
2. evitare decode completo di eventi che verranno scartati;
3. misurare quanto costa detector stateful + dedup;
4. rendere configurabile la doppia apertura ring/perf buffer se non necessaria;
5. aggiungere benchmark kernel-side con `bpftool`.

## Limite mitigato

Il detector demo inizialmente usava:

```yaml
group_by:
  - global
```

Questa scelta era pratica per l'MVP, ma troppo permissiva: poteva correlare
eventi non collegati tra loro se arrivavano nella stessa finestra temporale.
Il detector e' stato quindi prima ristretto a:

```yaml
group_by:
  - host_pid
```

`host_pid` riduce i falsi positivi perche' richiede che il cambio privilegi e
la successiva exec appartengano allo stesso PID visto dal namespace host.

La fase successiva ha introdotto:

```yaml
group_by:
  - process_tree
```

`process_tree` usa `host_pid`, `host_ppid`, `start_time` e
`parent_start_time` per correlare eventi dello stesso processo o di una
relazione parent-child. Non mantiene un albero processi globale: resta una
correlazione locale e breve.

Sono stati aggiunti anche tre detector collective:

- `privilege-sensitive-file-chain`;
- `memfd-exec-chain`;
- `kernel-module-kprobe-chain`.

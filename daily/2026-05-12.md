# 2026-05-12 - Merge libbpfgo, hook networking e output operativo

## Obiettivo

Portare il progetto verso una versione unica dopo il merge con il branch che
introduceva logica networking, mantenendo il tool eseguibile da CLI e
documentando i limiti emersi durante i test.

## Attivita' svolte

- Chiarito che il target Makefile deve buildare ed eseguire l'entrypoint
  ufficiale `cmd/project`, non il vecchio `main.go` nella root.
- Consolidato il passaggio lato userspace da `cilium/ebpf` a `libbpfgo`.
- Sistemati i flag CGO del Makefile usando `PKG_CONFIG_PATH`,
  `PROJECT_CGO_CFLAGS` e `PROJECT_CGO_LDFLAGS`, necessari per compilare
  `libbpfgo`.
- Aggiunto un target `filtered` per avviare rapidamente il tool su
  `security_socket_connect`.
- Integrati nel registry probe gli eventi networking del branch collaboratore:
  `security_socket_create`, `security_socket_listen`,
  `security_socket_connect`, `security_socket_accept`,
  `security_socket_bind`, `security_socket_setsockopt`,
  `security_socket_recvmsg` e `security_socket_sendmsg`.
- Aggiornato il protocollo decoder con gli argomenti degli eventi networking
  che possono essere decodificati.
- Ripristinata la funzione `events_ringbuf_submit` lato C per mantenere
  compatibili gli hook gia' migrati su ring buffer.
- Corretto il salvataggio degli argomenti degli hook process/security: gli
  indici argomento devono essere coerenti con `protocol.go`, non con il tipo
  dell'argomento.
- Verificato output leggibile in formato `table` per eventi come
  `sched_process_fork`, `task_rename`, `sched_process_exec`,
  `security_task_prctl`, `security_task_setrlimit` e `sched_process_exit`.
- Analizzato il significato di `args` nell'output: gli argomenti sono il
  payload specifico dell'evento kernel, non metadati generici.
- Chiarito come innescare manualmente `security_settime64`,
  `security_task_prctl` e `security_socket_connect`.

## Note tecniche importanti

Il runtime Go attuale inizializza:

```go
module.InitRingBuf("events_ringbuf", ...)
```

Quindi legge solo la ring buffer. Una parte degli hook networking importati dal
branch collaboratore usa ancora:

```c
events_perf_submit(&p);
```

Questo significa che gli hook possono essere compilati e attaccati, ma gli
eventi networking inviati su perf buffer non appariranno nell'output finche'
non verra' aggiunto un perf-buffer reader oppure finche' quegli hook non
verranno migrati a `events_ringbuf_submit`.

## Output e leggibilita'

L'output `table` ha reso piu' leggibili gli eventi rispetto al JSON raw:

```text
event=sched_process_exec pid=1612936 tid=1612936 uid=1000 comm=ls args=filename=/usr/bin/ls
```

Restano pero' argomenti ancora grezzi, ad esempio:

```text
event=security_task_prctl ... args=option=23,arg2=32,arg3=0,...
```

In questo caso `option=23` corrisponde a una costante `prctl`, probabilmente
`PR_SET_VMA`. Il prossimo miglioramento naturale e' aggiungere un layer di
mapping human-readable per opzioni `prctl`, resource limit, socket family,
socket type e syscall.

## Comandi utili verificati

Eseguire output compatto escludendo `cap_capable`:

```bash
make run_table
```

Eseguire con argomenti custom:

```bash
make run ARGS="--events task_rename,sched_process_exec,sched_process_exit --output table"
```

Testare `security_settime64`:

```bash
make run ARGS="--events security_settime64 --output table"
sudo date -s "$(date '+%Y-%m-%d %H:%M:%S')"
```

Testare una connect socket:

```bash
make filtered
python3 -m http.server 18080 --bind 127.0.0.1
curl http://127.0.0.1:18080
```

## Prossimi passi consigliati

- Decidere se usare ring buffer o perf buffer come canale unico.
- Se si mantiene perf buffer per networking, aggiungere il reader userspace.
- Se si sceglie ring buffer, migrare gli hook networking a
  `events_ringbuf_submit`.
- Aggiungere mapping human-readable per `prctl`, socket family/type e resource
  limits.
- Aggiungere filtri runtime piu' pratici, ad esempio per UID, PID o processo
  padre, per osservare meglio comandi come `ls` e `whoami`.

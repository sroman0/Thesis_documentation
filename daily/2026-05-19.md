# 2026-05-19 - Execve dedicata, log libbpf e direzione target-specific

## Obiettivo

Raffinare la prima demo dopo il merge e iniziare a spostare il progetto verso
una direzione piu' target-specific: meno genericita' rispetto a Tracee, piu'
aderenza al kernel Rocky/RHEL 8.10 usato nella VM di tesi.

Il kernel di riferimento e':

```text
Linux security-thesis-1 4.18.0-553.109.1.el8_10.x86_64
```

## Attivita' svolte

- Aggiunto l'evento `execve` come evento distinto da `sched_process_exec`.
- Chiarita la differenza semantica:
  - `execve` indica un tentativo di esecuzione;
  - `sched_process_exec` indica una exec riuscita.
- Spostato `execve` da un secondo hook generico su
  `raw_tracepoint/sys_enter` a un tracepoint dedicato:

```text
tracepoint/syscalls/sys_enter_execve
```

- Esteso `pkg/ebpf/probes/probes.go` con un nuovo tipo di attach:
  `tracepointProbe`, basato su `libbpfgo.AttachTracepoint`.
- Mantenuto `execve` sul path standard:
  `init_program_data(...)` + `events_perf_submit(...)`.
- Valutata e poi rimossa una prima implementazione di path leggero
  (`init_program_data_light` / `events_perf_submit_light`) perche' troppo poco
  versatile e piu' difficile da mantenere.
- Collegato il livello di log CLI `--log-level` al logger di `libbpfgo`.
- Filtrati di default i log `LIBBPF_DEBUG`, in modo da nascondere lo spam delle
  relocation CO-RE durante i run normali.
- Aggiornato l'help CLI per spiegare che `--log-level debug` mostra anche i log
  libbpf/CO-RE.
- Aggiornato il README con la nuova flag description e con `--comms`.
- Aggiornato il target `run_table` per testare `execve` senza filtro `--comms`,
  perche' al momento di `sys_enter_execve` il `comm` puo' ancora essere quello
  del processo chiamante.

## Decisioni tecniche

### Execve dedicata invece di secondo raw sys_enter

La prima versione di `execve` era agganciata a:

```c
SEC("raw_tracepoint/sys_enter")
```

e filtrava manualmente:

```c
if (id != SYSCALL_EXECVE)
    return 0;
```

Questo funzionava, ma il programma veniva eseguito per ogni syscall. La nuova
versione usa:

```c
SEC("tracepoint/syscalls/sys_enter_execve")
```

In questo modo il programma viene invocato solo per `execve`, riducendo il
costo kernel-side e rendendo piu' chiaro il significato dell'evento.

### Nessun path light per ora

E' stato provato un path piu' leggero per eventi semplici, ma e' stato rimosso.
Il motivo principale e' mantenere una pipeline uniforme:

```text
init_program_data -> events_perf_submit
```

La versione light avrebbe richiesto una seconda variante del protocollo di
inizializzazione, con il rischio di divergere dal path principale e introdurre
comportamenti difficili da spiegare.

### Log libbpf filtrati

I log come:

```text
libbpf: prog '...' relo #... <field_exists> ...
```

sono normali log di relocation CO-RE. Non sono necessariamente errori. Sul
kernel target alcuni campi, come `task_struct.start_boottime`, possono non
esistere e libbpf patcha il programma verso il fallback corretto.

La decisione e' stata:

- default `info`: nasconde `LIBBPF_DEBUG`;
- `debug`: mostra tutte le relocation libbpf;
- `warn`/`error`: mostra solo warning libbpf.

## Verifiche

Compilazione eBPF esplicita:

```bash
clang -O2 -g \
  -target bpf \
  -D__TARGET_ARCH_x86 \
  -D__x86_64__ \
  -I ./pkg/ebpf/c -I ./pkg/ebpf/c/common -I ./3rdparty/libbpfgo/libbpf/src \
  -c pkg/ebpf/c/project.bpf.c -o dist/project.bpf.o
```

Build userspace:

```bash
make build
```

Test package probe registry:

```bash
PKG_CONFIG_PATH=./dist/libbpf/obj \
CGO_CFLAGS="-I/home/simone/project/demo_project/dist/libbpf/include -I/home/simone/project/demo_project/3rdparty/libbpfgo" \
CGO_LDFLAGS="-L/home/simone/project/demo_project/dist/libbpf/obj -lbpf" \
go test ./pkg/ebpf/probes
```

## Problemi emersi

Il target Makefile `make bpf` non ricompila quando cambia un header `.h`
incluso da `project.bpf.c`. Per questo, dopo modifiche a file come
`common/context.h` o `common/buffer.h`, puo' essere necessario forzare la
ricompilazione dell'oggetto eBPF.

## Prossimi passi consigliati

- Aggiornare il Makefile per tracciare anche gli header eBPF nelle dipendenze
  di `dist/project.bpf.o`.
- Proseguire con altri hook syscall/security target-specific.
- Valutare filtri kernel-side per ridurre il costo di `--comms`.
- Continuare a documentare il trade-off tra compatibilita' generale e
  ottimizzazione per Rocky Linux 4.18.

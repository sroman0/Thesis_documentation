Verdict

Conditionally acceptable after targeted revision. No numerical error was found in the functional counts, timing spans or performance aggregates selected by the chapter. The functional narrative correctly distinguishes client outcome, kernel evidence and detector alert outcome. The principal unresolved issue is evidential rather than arithmetic: the archive does not preserve the applied monitor configuration and image identity for each performance replica, so the chapter currently states the causal effect of exact UID filtering more strongly than the archived evidence permits.

Findings by Severity

Major 1Filtered/unfiltered attribution is not independently reproducible per run

The selected raw samples reproduce the reported difference between the two monitored profiles. However, each Step 10 run directory contains deployment logs and measurements but not the rendered Pod manifest, monitor command line, image digest, or policy/detector hashes applied for that replica. The current scripts indicate that the intended profile difference is the exact UID filter, but the archive cannot prove after the fact that this was the only realised difference in all ten monitored runs.

Revise the claims around Chapter 6 lines 348--354 and 382--385 from a definitive causal statement to an observed profile comparison, for example: “Under the scripted profiles, enabling exact UID admission was associated with a reduction from 4.87% to 0.39% of one logical core.” Retain the causal interpretation as plausible, but qualify it until a rerun archives the applied manifest, exact command line, image ID and configuration hashes for every replica.

Moderate 2Sampling-window alignment needs a more exact limitation

Samples are selected when their endpoint timestamp lies between the workload start and end epochs, while each CPU value is a delta over the preceding sampling interval. The first selected interval can therefore include pre-workload activity, and the final partial workload interval can be omitted. The existing threat to validity mentions omitted boundary fractions but not possible first-interval contamination. State both effects explicitly. This does not invalidate the recomputed aggregates, but it constrains their temporal interpretation.

Moderate 3Some environment facts are documented but not preserved in raw evidence

The raw archive establishes Kubernetes client/server version 1.30.0, the applied Pod specification, container security contexts and image IDs. It does not independently preserve the claimed Minikube version 1.38.1, the complete Rocky Linux/kernel identity, or realised node capacity/allocatable resources. The chapter already distinguishes requested node sizing from realised capacity, which is correct. It should similarly identify the Minikube and host-version values as lab records unless those command outputs are added to the archive.

Moderate 4Technical claims require primary-source citations

Chapter 6 currently cites ATT&CK but leaves several externally verifiable claims unsupported. Add official references for Kubernetes Pod namespace sharing and security-context semantics, Minikube’s Docker driver, cgroup-v1 CPU-accounting units, and the upstream openECSC challenge provenance. Cite the exact ATT&CK technique pages if the individual technique meanings are discussed. Repository artefacts remain the source for this experiment’s concrete configuration; citations should support platform semantics, not replace the raw evidence.

Moderate 5Upstream revision pinning is not enforced by the preparation script

The preparation path verifies checksums for selected challenge artefacts, and the documentation records revision 2602f22c664eb98398413e6a7dfe03ea88b2d296. The script does not itself verify that the checked-out repository is at that revision. Describe the revision as a recorded experimental input, or add an explicit revision check and archive its output. The synthetic flag is correctly separated from upstream provenance.

Minor 6Small editorial and presentation issues remain

  • Replace the subjective description of the exploit workload as “more demanding” with a neutral statement of why it was selected.
  • Table 6.3 should state directly that cgroup memory and RSS entries are maxima over all selected samples and replicas, unlike the CPU mean.
  • The event sequence is introduced before the functional results and described again afterwards. Keep the protocol description brief and reserve field-level interpretation for the results.
  • The applied Pod automatically mounts the default service-account token. This need not dominate the body, but it belongs in the reproducibility record or deployment limitations.
  • RSS and Capture the Flag (CTF) are expanded in prose. Glossary entries are optional, but would improve consistency if these terms recur elsewhere.

Controls and Threats to Validity

The existing threats-to-validity section is appropriately cautious. It should retain and sharpen the following controls and limitations:

  • One Minikube node, one Pod topology and one challenge workload limit external validity.
  • Five replicas support descriptive comparison only; no inferential population claim should be added.
  • The no-monitor profile measures target behaviour without the monitor but does not isolate total tool overhead.
  • Node-level contention, SSH-mediated sampling jitter and cgroup-v1 accounting constrain attribution.
  • Per-run order was fixed rather than randomised or counterbalanced, so temporal drift can remain.
  • Boundary-selected intervals can include pre-workload CPU and omit final partial workload activity.
  • Exact configuration and image provenance are not archived for every Step 10 replica.
  • Three benign runs are a control for this scenario only, not a false-positive-rate study.

Redundancy and Chapter Boundaries

No substantial repetition against Chapters 2--5 was found. Chapter 6 does not repeat eBPF theory, the hook catalogue, the YAML schema or the user-space runtime walkthrough. The brief detector description is necessary to define the evaluated sequence, while the later result paragraph explains observed evidence. The latter can be shortened slightly, but neither passage should be removed entirely.

Full commands, manifests, raw JSON, per-sample TSV data, complete Pod descriptions, configuration hashes and image-build instructions correctly remain outside the body. They belong in the documentation archive or a reproducibility appendix. If an appendix is added, prioritise the exact applied-profile manifests and evidence inventory rather than reproducing all logs.

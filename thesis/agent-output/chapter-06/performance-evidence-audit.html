Measurement Boundary

Target and trigger tasksGenerate the controlled workload. Their container CPU and the scenario duration describe workload behaviour.
→
Kernel and eBPF hooksPrograms execute in the context of observed tasks. This cost is not reliably charged to the monitor container's cgroup.
→
Monitor containerConsumes perf records, decodes events and evaluates the detector. Its cgroup counters are the primary 5% gate.

The sampler runs on the Minikube node, outside the measured container. It reads cgroup v1 counters found under /sys/fs/cgroup/cpu,cpuacct/kubepods, /sys/fs/cgroup/memory/kubepods and /sys/fs/cgroup/pids/kubepods. Node activity is sampled separately from /proc/stat.

Attribution wording: “monitor-container CPU” or “CPU charged to the monitor cgroup” is more exact than “pure user-space CPU”. The latter is acceptable only as shorthand accompanied by the explicit exclusion of eBPF work charged to observed tasks.

Sampling and Workload Window

  1. The sampler starts before the workload and is configured for a 10-second warm-up, a 90-second maximum duration and a nominal one-second interval.
  2. The runner sleeps for ten seconds and records workload_start_ns immediately before kubectl exec.
  3. The trigger records an internal duration_ms for the exploit. The runner records workload_end_ns after kubectl exec returns.
  4. Run summaries select samples whose endpoint timestamp lies between the external start and end timestamps. They do not merely select every row marked measure.

The nominal one-second sampling period was not exact. Across the Step 10 files, observed intervals were approximately 1.02-1.70 seconds because each loop performs remote reads and calculations before sleeping again. CPU percentages remain normalised by the actual nanosecond interval, so this jitter does not invalidate the CPU formula.

Boundary qualification: each CPU sample is a delta over the interval ending at its timestamp. Selecting by endpoint means the first accepted interval may begin before the external workload start, while the last fraction before workload end may be omitted. The first accepted endpoints occurred 0.02-1.02 seconds after start; the final accepted endpoints occurred 0.01-1.02 seconds before end. The current method is adequate for minute-long descriptive runs, but not for fine-grained latency attribution.

The scenario's internal duration and the external sampling window are deliberately different. The former measures the exploit logic; the latter includes the surrounding kubectl exec overhead and is used only to select resource samples. Chapter 6 must not present them as the same clock interval.

Five-Percent Gate and Filtering Effect

Gate result: all five filtered run means are below 5% of one core. The largest filtered run mean is 0.41%, the mean of run means is 0.388% before display rounding, and the largest observed sample peak is 1.32%.

The 5% value is a predeclared engineering acceptance objective in NFR-07 and in the performance methodology. It is valid as a project-specific gate for explicitly defined profiles. No external evidence in the inspected material establishes 5% as a universal acceptability threshold, and it must not be generalised beyond this monitor configuration and workload.

The filtered-versus-unfiltered calculation is sensitive only in its last decimal place:

  • Published pipeline: (1 - 0.39 / 4.87) * 100 = 91.99%, using rounded aggregate values.
  • Unrounded run means: filtered 0.388%, unfiltered 4.868%, giving 92.03%.
  • Round-blocked reductions: 91.75%, 92.37%, 91.82%, 92.45% and 91.75%; mean 92.03%, sample SD 0.35 percentage points.

Recommended thesis wording: “In this controlled scenario, exact UID filtering was associated with an approximately 92.0% reduction in CPU charged to the monitor container relative to the otherwise equivalent unfiltered profile.” This preserves the result while avoiding false precision and total-overhead attribution.

Statistical Plan for a Small Repeated Experiment

  1. Experimental unit: treat each complete run as one observation. Do not treat the 48-63 time samples inside a run as independent replications.
  2. Primary summary: report the mean, sample SD, median, minimum and maximum of per-run monitor CPU means for filtered and unfiltered profiles.
  3. Tail behaviour: report each run's nearest-rank P95 and peak, then summarise the five P95 values descriptively. Never call P95 a confidence interval.
  4. Blocked comparison: compare filtered and unfiltered results within round as an exploratory blocked analysis because each round includes both profiles. Report the five differences or reductions, not only a ratio of grand means.
  5. Uncertainty: an exploratory Student-t interval may accompany a mean, clearly labelled as unstable with n=5. From rounded run means, filtered CPU is approximately 0.388% with a 95% t interval of 0.364-0.412%; unfiltered CPU is 4.868% with an interval of 4.726-5.010%. These intervals describe run-to-run uncertainty under this protocol, not future workloads or total overhead.
  6. Duration: retain mean, SD, median and full range. Avoid significance claims: one no-monitor run lasted 69.006 seconds and the node was nearly saturated.
  7. Memory: report run-level maxima and the maximum across runs. A future experiment should also retain per-run memory maxima in the aggregate input rather than only the overall maximum.
  8. Multiplicity and scope: designate filtered monitor CPU as the sole gate. Treat P95, peak, memory, target CPU, node CPU and duration as secondary descriptive outcomes.
Do not over-test five observations. Formal normality tests and precise inferential claims add little at this sample size. Transparent run-level values, blocked differences and bounded claims are more defensible.

Sources of Variability

  • The exploit runtime varies despite a constant reported worker count of 1793. Internal workload duration ranges from 51.450 to 69.006 seconds.
  • The two-vCPU node is close to saturation: profile-average node CPU is 94.70-95.11%, and every profile reaches 100% in at least one sample.
  • The sampling loop is nominally one second but includes command and file-read overhead, producing unequal intervals.
  • Every profile redeploys the Pod, creating fresh containers and cgroups but also introducing startup, cache and scheduling variation.
  • The cyclic order reduces simple monotonic drift but is deterministic and incompletely balanced over five rounds.
  • The trigger and monitor share node resources. Target CPU is lower on average in the unfiltered profile, so elapsed-time differences cannot be attributed solely to monitoring.
  • All measurements come from one node, one kernel, one day, one detector and one exploit scenario.

Discrepancies and Documentation Corrections

  • aggregate.tsv and the replicated report label the generic primary role correctly in prose, but future thesis tables should separate monitor and target metrics explicitly.
  • The phrase “0.02 sample standard deviation” in the Chapter 6 brief is ambiguous. It is the sample SD of five run-level means.
  • The 91.99% comparison is arithmetically reproducible but derives from rounded aggregate values. Retain no more than one decimal place in thesis prose.
  • The report's “P95 mean” is the arithmetic mean of five run-level nearest-rank P95 values. It is neither the P95 of pooled samples nor an uncertainty interval.
  • The current aggregate omits target P95, target maximum memory/RSS/PIDs and the primary peak CPU across runs, although these can be recovered from raw TSV and per-run summaries.
  • The Step 9 filtered exploit has scenario_status=1. It is valid as calibration of instrumentation and detection, but not as a successful workload repetition.

Missing Evidence

  • Direct attribution of eBPF execution cost, for example through a controlled hook-on/hook-off workload comparison with suitable system-level accounting.
  • A quieter or larger node where total CPU differences are not hidden by 93-97% average utilisation and repeated 100% peaks.
  • More repetitions, randomised or fully balanced order, and preferably independent experimental sessions.
  • A workload whose execution time is less variable, or a fixed-duration load generator with throughput as an outcome.
  • An interval-aware summary that clips counter deltas at workload boundaries or synchronises workload start with sampler intervals.
  • Longer stability measurements for memory growth, detector-state cleanup and sustained perf-loss behaviour.
  • A committed, immutable laboratory revision with image digests and retained host configuration sufficient to reproduce the exact evidence set.

Readiness Verdict

Ready for scoped descriptive reporting; not ready for a total-overhead conclusion.

The replicated evidence is internally consistent and sufficient to support three Chapter 6 results: the filtered profile satisfies the project-specific 5% monitor-cgroup CPU gate in five of five runs; filtered and unfiltered profiles preserve the expected alert and show no recorded loss diagnostic; and early UID admission is associated with an approximately 92.0% reduction in monitor-cgroup CPU in this controlled scenario.

The evidence does not establish total eBPF overhead, workload-latency equivalence, production performance or generality across nodes and workloads. Those claims remain blocked by attribution limits, near-saturated node CPU, five repetitions and a single experimental environment.

Chapter 6 Editorial Boundaries, Validity, Citations and Visual Audit

Editorial audit for Experimental Evaluation. This document does not draft the chapter. It defines the evidence boundaries, validity language, section ownership and acceptance conditions that should govern the later synthesis and LaTeX writing stages.

Executive Findings

Supported core claim. In the controlled single-node Minikube experiment, the selected collective detector distinguished the three observed benign executions from four executions that completed the configured malicious sequence. In the five replicated filtered runs, the monitor container's measured user-space CPU mean remained below the predefined 5% of one core threshold.
Authoritative kernel correction. The development and evaluation environment is Rocky Linux 8.10 running 4.18.0-553.137.1.el8_10.x86_64. The older 4.18.0-553.137.1.el8_10.x86_64 value in Chapters 1 and 3 is stale documentation and should be corrected before Chapter 6 is integrated. This is an editorial consistency issue, not evidence that the experiment used a different target from the implementation work.
Source-state note. The evidence records prototype commit 497da90f564c97fb9ffc38b264398150467173f5. The later working-tree differences do not materially change the kernel collection, decoding or detector capabilities exercised by the experiment, and the demonstrated behaviour is reproducible from the implementation baseline used by the preceding chapters. Configuration SHA-256 values, effective manifests and image digests should still be retained as ordinary experimental traceability data, without turning the commit difference into a principal validity concern.

The chapter should be framed as a scenario-based functional and resource evaluation. It is not a general detector-accuracy study, a Kubernetes deployment assessment, proof of loss-free collection, or a measurement of total eBPF system overhead.

Internal Profile order and temporal background-load effects Sequential runs on one busy node may differ because of scheduler state, cache state or unrelated host activity. The filtered, unfiltered and no-monitor order was rotated; each run recreated the Pod and cgroups and used a ten-second warm-up. Describe the rotation as mitigation, not randomisation. The sampler ran outside the monitor cgroup; workload measurement began after warm-up. State that sampling is excluded from monitor-cgroup accounting but not from total node contention.

A no-monitor profile and concurrent node/target metrics were collected. Call the result monitor-container user-space CPU consumption. Do not call 0.39% total overhead or subtract unlike primary metrics.
Construct CPU scale and percentile interpretation Container CPU is expressed relative to one core; the node metric uses total two-CPU capacity. The reported 7.72% is the mean of per-run P95 values, not a confidence interval. The raw per-run series and aggregation files are retained. Define both scales, label P95 precisely, and keep standard deviation descriptive.
Construct Different memory constructs Cgroup memory and process RSS do not measure the same allocation boundary. Both were recorded separately. Keep separate columns and definitions; do not combine them into one memory-overhead figure.
Construct Zero loss diagnostics is not proof of loss-free collection The diagnostic channel can report recognised perf-buffer loss, but it cannot prove that every expected operation generated, transported, decoded and retained a record. Loss diagnostics were counted, expected alerts were observed, and raw monitor logs were retained. Use “no perf-buffer loss was diagnosed in the observed runs”; never use “loss-free”.
Construct Alert validity versus attack success An LSM file-open observation establishes mediation, while the paired logical open event establishes a non-negative return. Neither alone establishes delivery of file contents to the client. The detector combines resolved-file and successful-open evidence; client output is recorded separately. Keep the three constructs distinct: kernel behaviour, detector match and end-to-end client outcome.
Construct hostPID: false interpretation The setting means the Pod does not request the node PID namespace. It does not make the monitor unprivileged or prevent eBPF programs attached to the node kernel from observing target tasks. The effective Pod manifest records hostPID: false and shareProcessNamespace: false. Describe empirical cross-container visibility through shared-kernel hooks. Also disclose privileged mode and host BTF, bpffs and tracefs mounts.
External Single Minikube node and one Pod The result does not cover multi-node scheduling, cluster aggregation, workload identity or distributed correlation. The scope is explicitly node-local. Keep every generalisation tied to the single-node laboratory.
External One challenge and one tailored detector A single CTF behaviour cannot represent production workloads, attack diversity or the full event catalogue. The challenge exercises a meaningful process burst and process/file sequence. Claim depth for this scenario, not general security coverage.
External Narrow benign control Three repetitions of one normal AES-beta path do not represent diverse legitimate activity. The benign path uses the same service and produces no configured malicious sequence. Do not estimate a false-positive rate. Identify broader benign testing as future work.
External Single kernel and host configuration The implementation and experiment were validated on one concrete Rocky Linux 8.10 build, 4.18.0-553.137.1.el8_10.x86_64. The thesis deliberately uses a target-aware design and records the exact environment. Limit portability claims to the validated environment. Correct the stale 553.137.1 references elsewhere in the thesis.
External Broad monitor privilege The monitor runs as root, privileged, with an unconfined seccomp profile and host kernel filesystem mounts. Target and trigger are non-root, drop all capabilities and use read-only root filesystems. State that the profile enables controlled evaluation but is not a production minimum-privilege design.
Conclusion Small sample sizes Three benign runs, four malicious runs and five runs per performance profile do not support population-level inference. All observations and descriptive statistics are retained. Use counts, ranges, means and sample standard deviations descriptively; avoid confidence, significance, accuracy, FPR or FNR claims.
Conclusion Overgeneralising the 91.99% reduction The value compares one filtered and unfiltered configuration under one workload and event scope. Profiles differ only in the UID filter and the order was rotated. Say “in this experiment” and identify the compared profiles; do not predict savings for other workloads.
Conclusion ATT&CK classification mistaken for coverage Two mapped techniques classify the configured behaviour but do not quantify detection breadth or validate the detector. Mappings are carried as detector metadata and preserved in alerts. Discuss interpretation only. Do not present a coverage percentage or matrix.

Challenge Specificity and Experimental Interpretation

AES-beta is a defensible controlled workload because the original binary, loader and glibc were verified by checksum and the exploit creates a substantial process burst followed by shell execution and sensitive file access. However, the laboratory is an adaptation rather than an unchanged deployment of the upstream challenge. It adds a listener, container packaging, a synthetic flag and a separate trigger container; it changes the endpoint and removes only the proof-of-work exchange. These changes should be summarised in Section 6.3, while checksums and the complete adaptation ledger belong in an appendix or supporting documentation.

The detector was deliberately derived from the observed offensive trace. Its four-step sequence is therefore a test oracle for the implemented policy/detector pipeline, not an independently developed general detector. The benign and malicious repetitions test consistency under the same laboratory conditions. They do not establish general sensitivity, specificity, false-positive rate or false-negative rate.

Appendix Boundary

The following material should not consume Chapter 6 body space:

  • complete Minikube start, image build/load, deployment, cleanup and log-extraction commands;
  • full Kubernetes manifests, ConfigMaps, Secret-generation commands and volume declarations;
  • full detector and policy YAML, which belong in Appendix B;
  • per-run raw samples, terminal output, full alert JSON, complete log windows and environment dumps;
  • all image digests, artefact checksums and the detailed upstream adaptation ledger;
  • the exploit implementation, proof-of-work removal details and low-level ROP construction;
  • calibration attempts superseded by the replicated protocol;
  • operational troubleshooting, root-run Minikube commands and abandoned hostPID: true evidence;
  • future networking evaluation and unrelated event families.

Appendix C should provide a concise, executable reproduction path and a stable evidence inventory. It should not become a chronological lab diary.

Terminology, Glossary, Labels and Structure

  • Use British forms: normalised, behaviour, artefact, organisation, optimisation.
  • Do not use the internal product name. Use prototype, monitor or monitoring system.
  • Use user space as a noun and user-space attributively. Qualify CPU as monitor-container user-space CPU.
  • Use point detector and collective detector; this experiment directly evaluates one collective detector.
  • Use cross-container visibility on the shared node kernel, not cluster-wide monitoring.
  • Use no perf-buffer loss was diagnosed, not loss-free collection.
  • Define P95 in prose as the 95th percentile. Do not treat it as an acronym or confidence interval.
  • Add glossary entries for CTF and RSS if each appears repeatedly. Add ROP only if the acronym remains in body prose more than once; otherwise spell it out locally.
  • hostPID, cpuacct.usage, Minikube and Kubernetes are names or literals, not glossary acronyms.
  • Use a consistent label family such as ch:experimental-evaluation, sec:evaluation-protocol, sec:evaluation-testbed, sec:functional-evaluation, sec:performance-evaluation and sec:threats-validity.
Chapter 1 wording. Chapter 1 currently promises evaluation of “CPU and memory overhead”. Given the implemented method, Chapter 6 should use resource consumption for its primary claim and explain why total overhead is not measured. The Chapter 1 sentence should eventually be aligned with that boundary.

Acceptance Checklist

Evidence and claims

  • The authoritative development and evaluation kernel 4.18.0-553.137.1.el8_10.x86_64 is reported, and stale 553.137.1 references in earlier chapters are corrected.
  • The reference commit, configuration hashes, effective manifests and image digests are recorded concisely as provenance metadata.
  • Calibration data are not mixed with the final five-run replicated results.
  • Three benign and four malicious functional runs are reported as counts, not general accuracy rates.
  • The divergent client run remains in the results and is interpreted separately from detector success.
  • The 0.39%, 4.87% and 91.99% claims name their exact profiles and metric boundary.
  • The no-monitor primary metric is identified as target CPU, not monitor CPU.
  • P95, standard deviation, range, cgroup memory and RSS are labelled precisely.
  • Zero diagnosed loss is not converted into proof of complete or loss-free telemetry.
  • ATT&CK mappings are used for classification and interpretation only.

Experimental boundaries

  • The chapter states that the environment is one Minikube node, one Pod and three containers.
  • hostPID: false is interpreted as a namespace setting, not as a reduction of the monitor's kernel privilege.
  • The monitor's privileged/root/unconfined profile and host mounts are disclosed.
  • The target and trigger non-root identities, dropped capabilities and read-only filesystems are recorded.
  • The exact UID filter is not described as a container or Kubernetes workload identity.
  • The detector's challenge-specific and post-observation tailoring is acknowledged.
  • No claims are made about multi-node correlation, enforcement, production minimum privilege or general attack coverage.

Editorial quality

  • Sections follow the canonical 6.1-6.8 structure.
  • Chapter 6 does not repeat hook theory, binary formats, YAML schemas, correlation internals or logging architecture.
  • Every result paragraph identifies the input, observation or metric, comparison and limitation.
  • Primary Kubernetes, Minikube, cgroup, upstream challenge and ATT&CK mapping citations have been added.
  • Glossary additions are limited to repeated acronyms and all terms follow British English conventions.
  • Figures and tables remain within the approved budget, are legible in greyscale and answer distinct questions.
  • Commands, full manifests, raw logs, full YAML and per-sample evidence are moved to appendices or stable supporting artefacts.
  • The evaluation summary introduces no new number or conclusion.

Binding Editorial Position

Chapter 6 should present a controlled case study that links an adapted but checksum-verified CTF workload to cross-container kernel observations, a challenge-specific collective alert and descriptive resource measurements. Its strongest contribution is the end-to-end validation of the implemented monitoring pipeline under a demanding process workload, together with a replicated demonstration that exact UID filtering sharply reduces the monitor container's user-space processing cost in this scenario. The credibility of the chapter depends on preserving the limits of that conclusion as carefully as the result itself.

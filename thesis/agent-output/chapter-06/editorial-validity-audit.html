1. Baseline and Claim Discipline

  • The topology consists of one DaemonSet monitor Pod, one Deployment-managed target Pod and one standalone trigger Pod on one two-CPU Minikube node.
  • The trigger reaches the target through a ClusterIP Service on TCP port 1337. The three Pods have distinct Kubernetes UIDs, IPs, container identities and Pod cgroups.
  • All Pods use hostPID: false. This demonstrates that the monitor did not depend on a shared host PID namespace; it does not isolate the Pods from the node kernel to which the eBPF programs are attached.
  • The monitor is root and privileged with unconfined seccomp. The target and trigger are non-root, drop all capabilities and use read-only root filesystems. A production least-privilege monitor profile was not evaluated.
  • UID 10001 is an exact kernel-side admission key for this experiment. It is not a Kubernetes workload identity, and unrelated node processes using that UID could pass the filter.
  • Three benign and three exploit functional runs were retained without replacement. The performance comparison uses three filtered and three unfiltered monitored runs. Three no-monitor runs are retained only as descriptive context.
  • “No diagnosed loss” means that the captured logs contained no matching perf-event loss diagnostic in the evaluated intervals. It is not proof that every generated kernel event reached user space.
  • ATT&CK identifiers classify the alert evidence. They do not establish technique coverage, detector accuracy or independent confirmation that a technique occurred.
  • The implementation revision used for evidence should be recorded as provenance, but the chapter need not centre a commit comparison: no material behaviour relevant to the stated findings differs from the implementation baseline described in the preceding chapters.

8. Language, Terminology and Structure Audit

  • Use British English consistently: normalisation, behaviour, artefact, utilisation, labelled and authorised.
  • Use kernel space and user space as nouns, and hyphenate adjectival forms such as kernel-side, user-space, cross-Pod and node-local.
  • Use “monitor”, “target” and “trigger” consistently for the three Pod roles. Do not alternate with “attacker Pod”, “client container” or “agent” without a defined reason.
  • The glossary already includes eBPF, CPU, MITRE ATT&CK, CTF, RSS, UTC and SD. No mandatory new acronym entry follows from the current body plan. Define P95 in prose; spell out TCP on first use if it recurs.
  • Use “Pod” with Kubernetes capitalisation, “Minikube” as a proper name and “cgroup” in lower case.
  • Reserve “success” for a stated criterion: application flag recovery, client validation, detector completion or profile threshold. Do not merge these into one ambiguous outcome.
  • Preserve the Chapter 6 section titles and numbering in the definitive outline. Labels should follow the existing thesis convention and be introduced once.

Chapter 6 Experimental Environment, Protocol and Reproducibility Audit

Scope: experimental environment, execution protocol and evidence preservation. Detector correctness and performance outcomes are deliberately excluded.

Audit baseline. The committed prototype was inspected at 497da90f564c97fb9ffc38b264398150467173f5 (fix(policy): fixed wrong configuration with --events and policy, 7 August 2026). This revision does not introduce behaviour material to the experiment: the monitored features and claims are also supported by the implementation baseline used in the preceding chapters. The revision difference is therefore a traceability note, not a threat to validity. The Minikube CTF laboratory is currently held as working-tree material under k8s/ and should be preserved with the experimental evidence. The adapted challenge source is a clean checkout of openECSC 2024 at 2602f22c664eb98398413e6a7dfe03ea88b2d296.

1. Executive Finding

The applied laboratory is sufficiently defined to explain a controlled, local experiment: one Minikube node runs one Pod containing a target, an attack trigger and the monitoring prototype. The target and trigger share the Pod network and communicate through localhost, while their process namespaces remain isolated. The monitor is the only privileged container and receives the host mounts required for eBPF operation.

The protocol is stronger than the original design in several respects. The challenge artefacts are checksum-controlled, container base images are digest-pinned, functional runs have identifiers, performance profiles are rotated, and the performance window is separated from warm-up. However, the current evidence collector does not preserve all the state needed to recreate a run: tool versions, node allocation, cgroup mode, applied ConfigMaps, image inventory and host/node clock alignment are absent or only indirectly recoverable.

Binding qualification for Chapter 6: describe this as a reproducible laboratory procedure with identified preservation gaps, not as a fully hermetic experiment. The experiment used Rocky Linux 8.10 kernel 4.18.0-553.137.1.el8_10.x86_64, not the earlier 4.18.0-553.137.1.el8_10.x86_64 build used as the implementation target elsewhere in the thesis.

Applied Pod Topology and Security Context

attack-trigger Benign and exploit client; UID/GID 10002 Non-root; privilege escalation disabled; read-only root filesystem; all capabilities dropped 64 MiB emptyDir at /tmp. No flag or host mount.
project-monitor Monitoring prototype; UID/GID 0 Privileged; seccomp Unconfined; read-only root filesystem Policy and detector ConfigMaps; host BTF read-only; bpffs and tracefs read-write; temporary workspace.

The Pod sets hostPID: false, hostNetwork: false and shareProcessNamespace: false. The three containers share the Pod network namespace, which is why the trigger reaches the target at 127.0.0.1:1337. They do not share a container process namespace and do not enter the host PID namespace. Storage is shared only through declared volumes. The namespace uses the privileged Pod Security level so that the monitoring container can be admitted.

The Pod does not set automountServiceAccountToken: false. Kubernetes therefore injects default service-account credentials into all three containers. This is not required by the experiment and weakens any claim that target and trigger receive only the explicitly declared resources.

Image and Challenge Provenance

  • The target and trigger Dockerfiles pin their base images by digest. The monitor image is rebuilt from the current local demo_project tree and loaded into Minikube under a mutable tag with imagePullPolicy: Never.
  • The applied Pod evidence records image IDs: target sha256:de73e8e4…, trigger sha256:4c9427d7… and monitor sha256:d9f9f1b1…. These IDs should be promoted to the primary environment table in the thesis evidence archive.
  • The challenge preparation script verifies the staged binary, loader and libc with SHA-256 values 44535b44…, 491c2eb0… and a7ec5ec3…. It does not verify that the openECSC checkout itself is at 2602f22….
  • The original binary, loader, libc, exploit payload and gadget assumptions are retained. The privileged challenge jail and proof-of-work front end are replaced by a bounded TCP wrapper suitable for the Pod experiment.
  • No competition flag is embedded. A Kubernetes Secret supplies a non-sensitive synthetic value only to the target. The default synthetic string is present in working-tree scripts and documentation, so the precise claim must be “no competition secret or static Secret manifest is committed”, not “the flag is never versioned”.

4. Protocol Timeline

  1. Freeze inputs. Record the implementation baseline, openECSC revision, current manifest/detector/policy hashes, image IDs, host/kernel, Docker, Minikube and Kubernetes versions.
  2. Create the cluster. Start a one-node Minikube profile with Docker, Kubernetes v1.30.0, 2 CPUs and 4096 MiB. Confirm node readiness, capacity and cgroup mode.
  3. Prepare and load images. Verify upstream challenge hashes, build the target and trigger from digest-pinned bases, build the monitor from the recorded source state, load all images and save the resulting image inventory.
  4. Deploy the laboratory. Create the namespace, policy and detector ConfigMaps, synthetic-flag Secret and three-container Pod. Wait for all containers to be ready and preserve the applied resources without storing the Secret value.
  5. Bootstrap check. Verify target reachability over Pod localhost and monitor startup. Capture timestamped logs and the Pod status, including image IDs and restart counts.
  6. Benign functional run. Generate or provide a unique run ID; capture trigger start/end records and timestamped monitor/target logs for the same interval.
  7. Exploit functional run. Execute the fixed AES-beta exploit workload with its bounded worker count and the same evidence procedure. Repeat according to the declared run count.
  8. Performance suite. For each of five rounds, recreate the Pod under the rotated filtered, unfiltered and no-monitor profiles. Start sampling, wait 10 seconds, execute the 90-second workload window and preserve raw samples before calculating summaries.
  9. Close the experiment. Archive raw evidence, configurations, hashes, run IDs and environment metadata before deleting the Pod or Minikube profile. Generate summaries from immutable raw data.

Clock, Run and Configuration Preservation

The laboratory currently combines Python wall-clock epochs from the trigger, UTC listener timestamps, Kubernetes log timestamps, host nanoseconds and Minikube-node nanoseconds. The performance summary selects node samples using host-derived workload boundaries. This is valid only if host and node realtime clocks are sufficiently aligned; the scripts do not measure that offset. The chapter must either document an explicit synchronisation check or treat alignment as a source of measurement uncertainty.

The automatic evidence collector preserves the Kubernetes version, Pod YAML, Pod description, namespace events and timestamped container logs. It does not preserve the openECSC revision, host and Minikube versions, node allocation, cgroup mode, ConfigMap contents, image inventory, configuration hashes or client scenario output. The final campaign should extend this snapshot before any result is presented as independently repeatable.

9. External Sources Required

Use primary documentation for platform semantics; local files remain the source for the realised configuration.

  • Kubernetes networking model: one private network namespace shared by containers in a Pod and communication over localhost.
  • Kubernetes process namespace sharing: meaning and consequences of shareProcessNamespace.
  • Kubernetes security contexts: non-root identity, privilege escalation, capabilities, privileged mode and seccomp.
  • Kubernetes hostPath volumes: host exposure and security/reproducibility risks.
  • Service-account credential automounting: default token injection and opt-out.
  • Minikube start command and Docker driver: driver, Kubernetes version and resource flags.
  • Linux cgroup v1 CPU accounting and memory controller: interpretation of the raw counters.
  • Pinned openECSC AES-beta source: challenge provenance.

10. Visual Proposal

One primary environment figure: draw the Rocky Linux host and single Minikube node, then one Pod containing three clearly differentiated containers. Show a shared Pod network with the trigger-to-target connection over 127.0.0.1:1337; separate PID namespaces; a read-only Secret mounted only into the target; policy/detector ConfigMaps mounted into the monitor; and the monitor's BTF, bpffs and tracefs host mounts. Mark the monitor as root/privileged and the other two as non-root/unprivileged. Add hostPID=false and “no shared process namespace” next to the Pod boundary.

The figure should answer one question: which isolation boundaries are preserved, and which resources are deliberately shared to execute and observe the attack? Do not place protocol results or detector output in this figure. A compact protocol timeline may be a second visual only if prose becomes difficult to scan; it should show freeze, deploy, warm-up, workload, sampling and evidence archive.

11. Chapter 6 Paragraph Plan

  1. Evaluation purpose and boundaries. Define the CTF-based functional experiment and the separate resource protocol. State that the chapter evaluates a local prototype, not cluster-wide monitoring.
  2. Host and Minikube baseline. Report Rocky Linux 8.10, the actual kernel build, Minikube/Kubernetes versions, driver, node count and requested node resources. Qualify the difference from the original target kernel build.
  3. Pod topology and isolation. Explain the one-Pod/three-container arrangement through the proposed figure, with network sharing, PID isolation, UIDs, privileges and mounts.
  4. Challenge adaptation and provenance. State the pinned openECSC revision, artefact checksum controls, retained exploit mechanics, replaced listener/PoW boundary and synthetic flag handling.
  5. Applied monitoring configuration. Identify the policy, detector and image/configuration hashes needed to reproduce the experiment without analysing detection quality.
  6. Functional protocol. Describe bootstrap, benign and exploit scenarios, run identifiers, repetitions and evidence captured for each run.
  7. Performance protocol. Define the three profiles, five rotated rounds, warm-up, workload window, sampling interval and raw counters. Explain that rotation is deterministic and that no-monitor changes the measured entity.
  8. Variables and evidence. Summarise controlled, independent and dependent variables; state clock, source-state, image and configuration preservation.
  9. Threats to reproducibility. Report absent resource limits, mutable image tags, missing clock-offset capture and incomplete environment snapshot.
  10. Transition to results. Separate this method from later detector and performance findings so that results do not retroactively redefine the protocol.

12. Unresolved Issues, Ordered by Priority

  1. Extend the evidence snapshot before the final campaign. Add environment versions, node description, cgroup mode/paths, applied ConfigMaps, image inventory and configuration hashes.
  2. Measure clock alignment. The current host-defined workload interval is applied to node timestamps without a saved offset or uncertainty.
  3. Resolve resource-control wording. Either add justified container limits or explicitly state that only requests were configured and treat contention as a threat to validity.
  4. Pin the challenge revision mechanically. Fail preparation if the openECSC checkout is not at 2602f22….
  5. Disable unused API credentials. Set automountServiceAccountToken: false unless a container demonstrably requires Kubernetes API access.
  6. Freeze Minikube and Docker identity. Record, and preferably provision, the exact executable/engine versions used for the final runs.
  7. Choose the authoritative repetition counts. Preserve them in the protocol and scripts, avoiding divergent narrative values.
  8. Preserve the laboratory artefacts. Archive the applied manifests, scripts, policy and detector with the evidence; this is an organisational requirement rather than a concern about the prototype revision.
  9. Clarify image preservation. Decide whether image IDs plus build metadata are sufficient or whether the three final images will also be exported and checksummed.

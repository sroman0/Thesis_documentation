Chapter 6 Functional Evidence and Collective-Detector Audit

This report audits the functional evidence for the AES-beta Minikube experiment. Counts and event properties were regenerated from the raw JSONL, per-run summaries, scenario output and monitor logs. Narrative evaluation documents were treated as claims to check, not as count authorities.

Audit Verdict

Ready for a scoped functional evaluation. The available artefacts support cross-container event visibility with hostPID: false, zero AES-beta alerts in three narrow benign controls, and one four-event collective alert in each of four observed malicious sequences. Every alert is high, contains the expected ordered evidence, and carries the configured ATT&CK metadata.
The evidence does not estimate general detection accuracy, prove that no perf record was lost, or validate the immediate parent-child branch of process_tree in the live laboratory. The four live alerts progressed through one stable host PID; parent-child correlation is established separately by shared detector tests.

Cross-Container Visibility with hostPID: false

The applied Pod ran the target as UID 10001 and the monitor as a separate privileged container. Both hostPID and shareProcessNamespace were false. During the isolated Step 6 stimulus, the monitor emitted nine UID-10001 records with UTS name aes-beta-lab. The controlled cat appeared as PID 327 in its PID namespace and host PID 3016236 in the host identity fields. Its records included the completed executable transition, the resolved path /opt/aes-beta/flag, and an open result of file descriptor 3.

Together, the applied namespace settings and the target-identified records support the claim that the eBPF monitor observed activity from another container without joining the host PID namespace. The result is node-local: the containers share the Minikube node kernel, and no cross-node observation was tested.

The divergent third exploit

The third client returned an empty flag and exit status 1, while the target listener recorded a completed session with exit code 0. The alert independently preserves successful shell and cat transitions, resolved-file mediation and a non-negative open result. The defensible conclusion is that the monitored host-side sequence completed although the client did not receive the expected application output. The evidence does not identify where output delivery failed, so the run must not be described simply as either a fully successful exploit or a detector false positive.

Paragraph Plan for the Functional Evaluation

  1. Evaluation target and controls. State that the experiment evaluates one known four-observation sequence, with a benign interaction as a negative control. Refer back to Chapters 3 and 5 for detector theory and implementation.
  2. Cross-container visibility. Present the applied namespace settings and the Step 6 PID/host-PID evidence. Explain only the experimental consequence: observation came from the shared node kernel.
  3. Evidence semantics. Use one short paragraph to distinguish completed executable transitions, LSM mediation and successful syscall return. Avoid repeating the hook implementation from Chapter 4.
  4. Collective result. Present the four ordered event types and report that all live alert records use one host PID and fall inside the configured window.
  5. Repeated runs. Use one compact table for three benign and four exploit windows, preserving the diagnostic fourth exploit and the divergent third client.
  6. Divergent client interpretation. Separate host-side detection from application-output delivery and avoid assigning an unobserved root cause.
  7. Claim boundary. State that the experiment demonstrates deterministic integration for this controlled scenario, not general detection accuracy, loss-free collection or parent-child correlation in live traffic.
Material already owned elsewhere. Do not re-explain YAML fields, state maps, pruning, deduplication, process-tree key extraction, ATT&CK propagation or the distinction between point and collective detectors. Chapters 3 and 5 already own those mechanisms.

Unresolved Issues for Synthesis

  1. Correlation key observability. The alert JSON omits task and parent start times. Decide whether to state only that the configured detector completed and that all evidence shared one host PID, or to add a future output field before claiming direct reconstruction of the stable process key.
  2. Step 7 naming. step7-final-telemetry.jsonl contains eight direct-cat events and no alert or shell event. It should support visibility, not the live collective result.
  3. Complete-log extra alert. The complete monitor log contains one valid alert at 05:55:55 UTC before the Step 8 protocol. Only the four windowed per-run logs should determine the repeated exploit count.
  4. Loss wording. Every summary reports zero loss diagnostics, and an independent text search found no matching loss message in the windowed monitor logs. The exact Step 8 aggregation command is not retained in the inspected scripts, and no independent sequence-number or transport-counter measurement is present.
  5. Negative-control breadth. No live controls deliberately test wrong order, wrong UID, failed open, timeout expiry or a similar benign shell-and-file chain. These are possible extensions, not prerequisites for the scoped result.
  6. Divergent client cause. The available records show successful target-session completion and host-side file open, but not why exploit 3 returned an empty flag. Preserve the uncertainty.
  7. Terminology conflict. The style guide still prescribes “collective anomaly”, while the current Chapter 6 brief prefers “collective detector”. The chapter should use “collective detector” and “collective alert” unless the definitive terminology guide is updated centrally.

1. Authority and Editorial Constraints

This specification resolves the four audit reports against the applied manifests, detector definition, scripts and raw evidence. Raw artefacts take precedence over summaries; source files take precedence over design intent. The chapter must be approximately 2,800-3,500 words and 12-14 pages. It may contain at most three figures and three result tables, and no source-code listings.

The chapter evaluates one integrated laboratory case study. It may claim observation of cross-container host events, completion of one deterministic collective detector sequence, behaviour in the repeated benign and exploit runs, resource consumption attributed to the measured cgroups, and the scenario-specific effect of exact UID filtering. It must not claim general detection accuracy, total system overhead, statistical significance, loss-free transport, cluster-wide correlation or Kubernetes deployment readiness.

Present the former as the implementation target and the latter as the exact experimental patch-level build. Step 6 record count The complete file contains 7,289 records, not nine. Exactly nine have UID 10001 and correspond to the directly invoked target-side cat workflow. “Nine UID-10001 records were isolated from the captured stream.”
Cross-container visibility The monitor observed target-container activity using host identifiers while hostPID and shared process namespaces were disabled. This is same-node kernel visibility, not cluster-wide visibility. Claim node-local observation across container boundaries within the Pod; do not claim Kubernetes-wide process visibility.
Exploit repetition All four exploit windows produced one four-event alert. Three returned the synthetic flag to the client; the third returned an empty flag and exited with status 1 despite the observed shell, cat and successful open. Separate detector completion from application-output delivery. The divergent run is evidence that these are different outcomes.
LSM evidence security_file_open records mediation-stage resolved object evidence. Success is established only by the later open event with a non-negative return value. Describe the third event as mediation and the fourth as syscall success evidence.
Collective correlation All four evidence events in each live alert share one host PID. The experiment exercises the same-process key accepted by process_tree; it does not independently validate the immediate parent-child branch. Claim successful local same-process sequence correlation only.
Loss reporting No matching perf-loss diagnostic appears in the selected windows or the ten monitored performance runs. Diagnostic absence cannot prove that no record was lost. “No loss diagnostic was reported,” never “no events were lost.”
No-monitor profile Its primary metric is the target cgroup, whereas the monitored profiles use the monitor as primary. The columns are not directly comparable as one generic “primary CPU” measure. Use no-monitor only as workload context; do not subtract it to estimate total monitor overhead.
Five per cent threshold The threshold is a project-defined acceptance gate for mean CPU charged to the monitor cgroup, expressed as a percentage of one core. It is not a general security-monitoring standard. State its local definition once in the protocol and report whether each run met it.
Claims blocked unconditionally: “100% detection accuracy”, false-positive or false-negative rates, “zero packet/event loss”, “loss-free perf transport”, “less than 5% total overhead”, causal improvement in workload duration, statistical generalisation beyond the observed runs, and successful cluster-wide or enforcement behaviour.

Functional protocol timeline

  1. Start the pinned Minikube profile and deploy the namespace, policy, detector, synthetic flag and three-container Pod.
  2. Wait for Pod readiness and preserve the applied Pod, image identities, Kubernetes version and configuration hashes.
  3. Verify same-node workload telemetry with hostPID: false and isolate UID-10001 target records from the wider monitor stream.
  4. Execute three benign windows and four exploit windows with unique run identifiers. Capture scenario output, stderr and time-bounded logs from all containers.
  5. Count only alerts and loss diagnostics inside each preserved window; do not use the complete accumulated monitor log as a run total.

Performance protocol timeline

  1. Run five rounds. Rotate profile order cyclically: filtered, unfiltered, no-monitor; then shift the starting profile in subsequent rounds.
  2. Recreate the Pod and wait for readiness before every profile run.
  3. Start cgroup and node sampling, allow a 10-second warm-up, then execute the exploit workload. The nominal run ceiling is 90 seconds, while the workload determines the actual selected interval.
  4. Select samples whose timestamps fall within the externally recorded workload boundaries. Preserve per-run TSV, summary, scenario output and monitor log where present.
  5. Aggregate the five run means per profile and retain the individual values for the paired visual. Treat ordering as rotated, not randomised.

The requested node capacity is recorded by the launch command, but a realised capacity/allocatable snapshot is not archived. The sampling path uses cgroup v1. Sampling intervals varied in practice because each read was performed through the Minikube SSH path.

Permitted numerical statements

  • Across five filtered exploit runs, mean CPU charged to the monitor cgroup ranged from 0.36% to 0.41% of one core; all five run means were below the project-defined 5% gate.
  • The corresponding unfiltered monitor run means ranged from 4.73% to 4.98%, with an aggregate mean of 4.87%.
  • The filtered mean of 0.39% was approximately 92.0% lower than the otherwise equivalent unfiltered mean of 4.87% in this workload. The raw calculation from run values is approximately 92.03%; the archived rounded summary reports 91.99%. Use “approximately 92.0%”.
  • All ten monitored performance runs emitted exactly one alert and no matching textual loss diagnostic.
  • Mean node CPU was 94.70%, 95.11% and 94.89% in filtered, unfiltered and no-monitor profiles respectively. This near-saturation is a required qualification for workload-duration comparisons.

Metric interpretation

Container CPU is derived from cgroup-v1 cpuacct.usage deltas divided by wall-clock deltas and expressed as a percentage of one core. Node CPU is calculated from /proc/stat and uses the full two-core node as its 0-100% scale. Cgroup memory includes more than resident process pages and must not be labelled RSS. RSS is reported separately from memory.stat. The no-monitor row measures the target because no monitor cgroup exists.

Do not infer from the shorter filtered mean workload duration that the filter caused a speed-up. The node was highly utilised, only five runs per profile were collected, profile order was rotated rather than randomised, and the target workload itself varied. Do not combine the three “primary” columns without naming their different container owners.

12. Threats-to-Validity Structure

Internal validity. Profiles were rotated cyclically rather than randomly assigned. Pod recreation reduces state carry-over but does not remove host load or cache effects. Sampling through Minikube SSH produced intervals above the nominal one second, and the first/last workload fractions may not align perfectly with selected samples. The node remained close to saturation. The third exploit run had a client-output failure even though the host-side sequence completed.

Construct validity. Monitor-cgroup CPU is not total system overhead; no-monitor target CPU cannot be subtracted from it. Cgroup memory and RSS measure different quantities. The four kernel timestamps do not measure alert latency. A missing textual loss diagnostic does not prove loss-free perf transport. An LSM hook reports mediation, while syscall return evidence is required for success. ATT&CK labels classify the detector but do not validate it.

External validity. Results come from one Rocky Linux kernel build, one Minikube node, one Docker-backed Kubernetes version, one public CTF workload, one tailored collective detector and one synthetic flag. The benign workload is narrow. No multi-node, production orchestration, alternative kernel, workload mix or long-duration campaign was evaluated.

Conclusion validity. Five runs per performance profile and seven functional windows support descriptive statements, not inferential statistics or accuracy rates. The approximately 92% filtering reduction is specific to the selected workload, event scope, UID and saturated laboratory node. Duration differences must not be presented as causal.

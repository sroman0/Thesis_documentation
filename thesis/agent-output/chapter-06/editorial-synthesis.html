Supported central finding. On the evaluated single-node Minikube environment, a privileged monitor Pod observed a four-event attack sequence generated in a separate target Pod and initiated from a third trigger Pod. The sequence completed in all three retained exploit runs and did not complete in the three retained benign controls. In the performance campaign, the exact UID-filtered profile used a mean of 0.46% of one CPU core in the monitor cgroup across three runs, compared with 5.73% for the otherwise equivalent unfiltered profile. These are node-local, scenario-specific observations, not detection-accuracy, total-overhead or production-readiness claims.

3. Paragraph-Level Narrative Plan

6.1 Evaluation Objectives and Experimental Protocol

  1. Bridge from Chapter 5: the implementation is complete enough to evaluate whether node-level collection, policy admission and collective detection behave as designed in a containerised scenario.
  2. State three objectives: verify node-local cross-Pod visibility; verify the configured four-event detector on exploit and benign controls; measure monitor-cgroup CPU and memory with and without exact UID admission.
  3. Define the evidence oracles separately: application outcome, detector outcome and operational health. Client validation is a fourth harness check and must not replace the application oracle.
  4. Define independent variables: workload class for functional runs and monitor profile for performance runs. Define dependent variables: recovered flag, complete alert count/order, diagnosed loss, restart delta, CPU, memory and RSS.
  5. Summarise repetitions and rotated profile order. Refer readers to archived documentation for commands and raw artefacts.

6.2 Cross-Pod Minikube Experimental Testbed

  1. Identify Rocky Linux, kernel, Minikube, Docker driver, Kubernetes server and requested node resources in one concise environment table.
  2. Explain the three separate Pods on one node: privileged monitor DaemonSet, non-root target Deployment and non-root trigger Pod connected through a ClusterIP Service.
  3. Explain that all Pods have hostPID: false and distinct Pod identities, IPs and cgroups, but share the node kernel observed by eBPF. This supports node-local cross-Pod visibility, not cross-node monitoring.
  4. State the relevant security contexts and mounts once. Explicitly distinguish sufficient laboratory privilege from a minimised production deployment.
  5. Introduce Figure 6.1 and close with the exact experimental boundary.

6.3 AES-beta Workload and Controlled Attack Scenario

  1. Identify the pinned openECSC challenge and synthetic flag. Explain only enough vulnerability context to justify the workload; exploit mechanics belong in supporting documentation.
  2. Describe the benign control and the exploit's final application effect: command execution leading to shell and cat activity and access to the mounted flag.
  3. Describe the experimental policy and detector as configuration, not implementation: UID 10001, four ordered events, five-second window and process_tree correlation.
  4. Use the corrected two-panel exploitation/evidence figure to map application actions to sched_process_exec, security_file_open, successful open and the final alert.
  5. State that ATT&CK metadata classifies the configured evidence and is not an experimental measure of technique coverage.

6.4 Functional Evaluation

  1. Establish cross-Pod visibility from run-local monitor logs and effective topology artefacts, without repeating the hook or decoder implementation.
  2. Report that all three exploit runs recovered the synthetic flag and produced exactly one complete four-event alert. Explain that the same-process branch of process_tree was exercised; the parent-child branch was not independently tested.
  3. Report that all three benign controls produced the expected benign response and zero matching alerts. Do not calculate a false-positive rate.
  4. Present all six runs in one result table, preserving the delayed first benign run and the two client-pattern failures.
  5. Close with zero restart deltas and no matching loss diagnostic in the six intervals, using qualified wording.

6.5 Performance Evaluation

  1. Define monitor-cgroup CPU as a percentage of one core from cgroup-v1 CPU accounting. Define cgroup memory, RSS and node CPU separately.
  2. Describe three filtered, three unfiltered and three contextual no-monitor runs, the ten-second warm-up, nominal 75-second sampler, actual host-timestamped workload window and rotated order.
  3. Report filtered and unfiltered CPU and memory in one table. State that the sample standard deviation is across three run means and that mean run P95 is descriptive, not a confidence interval.
  4. Evaluate the project gate: each filtered run mean was below 5% of one core. State that the unfiltered profile exceeded it.
  5. Report the 91.97% reduction only as the difference in monitor-cgroup CPU between these controlled profiles. Do not call it total system or total eBPF overhead.
  6. Use no-monitor target/node values only as context. Exclude duration-based causal conclusions because of node saturation and unresolved termination timing.

6.6-6.8 Interpretation, Validity and Closure

  1. Discussion: combine the supported findings without restating every value. Emphasise that exact early admission materially reduced user-space monitor demand while retaining the expected alert in this workload.
  2. Threats: organise limitations under internal, construct, external and conclusion validity. This is the sole owner of caveats already introduced briefly next to results.
  3. Summary: answer the three objectives in one paragraph and bridge to Chapter 7, where broader limitations and future work are synthesised rather than introduced as new evaluation results.

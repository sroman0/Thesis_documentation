Executive Findings

  1. The runtime has three semantic outputs but only two operating-system channels: normalised security events and detector alerts share stdout, while Zap diagnostics use stderr. Fatal command and lifecycle errors also use stderr, but bypass Zap.
  2. The decoder event and detector alert are internal models. pkg/output owns their public JSON and compact-text representations and the conversion of numeric kernel values into readable labels.
  3. JSON preserves typed argument values and adds optional labels; compact text replaces selected raw values with readable forms. The two conversion paths currently duplicate a long event-specific dispatch, creating a drift risk.
  4. Point alerts present one source event. Collective alerts preserve an ordered evidence sequence; compact text bounds its rendering to 1,024 bytes plus an ellipsis, while JSON retains the event array.
  5. Zap supports console and JSON encodings, four levels, and a dedicated libbpf callback. It is correctly excluded from security-data serialisation. The local changes now log and propagate project cleanup failures, but logger flush errors remain ignored and fatal setup errors still return through main.
  6. The two-stage image embeds the eBPF object in the Go executable and copies only that executable into the runtime stage. Policy and detector YAML catalogues are not packaged and therefore require explicit external delivery.
  7. The current README overstates the Docker workflow: it documents a dev stage and Make targets that do not exist, gives a different default image tag, and claims tracefs/debugfs mounts that docker-run does not currently apply.
  8. Container execution is implemented as a privileged host-integrated Docker path. Kubernetes deployment is not implemented or validated: there is no manifest, privilege minimisation, host-resource contract, or operational lifecycle evidence.

Data Models and Presentation Ownership

Normalised event

bufferdecoder.Event is the internal event passed to policies, detectors, and output. It contains an EventContext, an event name, and typed arguments. The output layer converts it into an unexported eventRecord with process, host, kernel, and argument groups. This is the actual JSON schema used for both ordinary event output and alert evidence.

Evidence loss at the presentation boundary. The internal context contains process start times, cgroup ID, leader and parent start times, flags, and stack ID. eventRecord does not expose those fields. Consequently, JSON evidence may omit the stable identities that a collective detector used to correlate events. Chapter 5 may describe the current schema, but should not call it a complete serialisation of the normalised event.

Detector alert

detectors.Alert is the preliminary detection result: detector identity, title, description, severity, creation time, evidence events, threat metadata, and free-form metadata. output.AlertRecord is the presentation model. It normalises every evidence event through the same eventRecord, derives sorted policy names from alert metadata, and converts threat metadata into an explicit JSON object.

Human-readable adaptation

argumentViews adds symbolic labels to JSON without replacing typed values. formatArg renders compact-text values such as symbolic capabilities, signals, operation names, permission masks, hexadecimal pointers, file descriptors, and errno descriptions. Both are implemented in pkg/output/event.go. This is presentation logic, not decoding: the decoder remains responsible for type-safe binary interpretation.

The architectural statement should be concise: the decoder establishes type and value, while the output adapter establishes public shape and human-readable labels. An exhaustive list of mappings belongs in an appendix or generated reference.

Zap and libbpf routing

pkg/logging.New builds a production-style Zap logger with stderr as both normal and internal error sink. Supported encodings are console and JSON; supported levels are debug, info, warn, and error. Caller annotation and stack traces are disabled. The libbpf global callback trims the trailing newline, adds source=libbpf and the numeric libbpf level, maps libbpf warnings to Zap warnings, and maps other accepted messages to Zap debug.

At debug level the callback accepts all libbpf messages. At info it filters libbpf debug records, while non-warning records that pass the callback are still emitted at Zap debug and therefore suppressed by the logger level; warnings remain visible. At warn only warnings remain visible. At error, warning callbacks can pass the filter but are suppressed by Zap's error threshold. This behaviour is implementation-specific and should be described as verbosity control, not as a lossless level translation.

External catalogue contract

The CLI accepts policy and detector file or directory paths. Because the runtime image contains neither catalogue, a container invocation that uses YAML rules requires the files to exist inside the container at the paths passed to --policy and --detectors. No current Make target establishes that mount. This is a packaging gap, not a detector-engine limitation.

type Printer interface {
    Print(event bufferdecoder.Event) error

func NewPrinter(format string, w io.Writer) (Printer, error) {
    switch format {
    case "json":
        return NewJSONPrinter(w), nil
    case "table":
        return NewTablePrinter(w), nil
    default:
        return nil, fmt.Errorf("unsupported output format %q", format)
    }
}

  3. Should alert evidence expose process start time, parent start time, cgroup ID, and other stable identifiers used by correlation?
  4. Should output write failures terminate the runtime, trigger bounded retries, or remain non-fatal as currently implemented?
  5. Should fatal setup errors occurring after logger construction be logged through Zap before they are returned, while avoiding duplicate messages in main?
  6. Should logger.Sync errors be surfaced with the same policy now used for Project.Close?

Handoff Conclusion

The strongest Chapter 5 narrative is not a catalogue of printers, flags, and files. It is an ownership argument: decoded events retain their security meaning, the output layer adapts them for human or machine consumption, detector alerts preserve the observations that caused a match, and operational diagnostics remain outside both security-data models. The container then packages the executable and embedded eBPF object, while deliberately exposing unresolved dependencies on host kernel resources and externally supplied rule catalogues.

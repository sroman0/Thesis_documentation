5. Exact Reusable Chapter 6 Statements

Functional statement

“In the evaluated single-node Minikube environment, the privileged monitoring Pod observed the selected target activity while the target and trigger ran in separate Pods on the same node. All three exploit repetitions recovered the synthetic flag and produced one complete four-event alert from the configured collective detector, whereas the three repetitions of the selected benign interaction produced no matching alert.”

Required boundary: this supports same-node cross-Pod visibility and repeatability for one configured scenario. It does not support cross-node visibility, general detection accuracy, a false-positive rate, complete event coverage or experimental validation of every correlation strategy. Client validation passed in only one exploit run because of the documented harness expression, while flag recovery and detector completion succeeded in all three; omit that detail from the main conclusion only if Section 7.2 clearly attributes “success” to flag recovery and detector evidence.

Performance statement

“Across three runs, the exact UID-filtered profile used a mean of 0.46% of one CPU core in the monitor-container cgroup, so every filtered run remained below the project’s 5% gate. The corresponding unfiltered mean was 5.73%; using the preserved unrounded data, the filtered mean was approximately 92.0% lower while the required flag recovery and complete alert were retained in every monitored run.”

Required boundary: the metric is monitor-container cgroup CPU as a percentage of one core. It excludes parts of kernel execution charged elsewhere and is not total eBPF, node or system overhead. The comparison is scenario-specific and descriptive. No-monitor duration must not be used for causal inference because final monitor-Pod disappearance was not independently timestamped.

Optional operational statement

“No matching perf-event loss diagnostic and no Pod restart delta were observed during the retained functional and monitored performance runs.”

Required boundary: this describes recorded indicators only. It is not proof of complete delivery or loss-free transport. Memory maxima may be omitted from Chapter 7; if retained, cgroup memory and total_rss must remain separate descriptive metrics.

6. Ranked Future-Work Directions

  1. Generate and continuously verify the event contract. This addresses separately maintained event IDs, schemas, probe exposure and binary layout constants. First repair the present support-probe classification; then derive cross-language metadata from one reviewed source and make consistency tests mandatory in CI.
  2. Add object-backed lifecycle and compatibility testing. This addresses limited assurance for object resolution, selective loading, map configuration, attachment routes, partial-failure rollback, cancellation and cleanup. Combine deterministic injected-failure tests with a small privileged smoke suite on the supported Rocky Linux kernel.
  3. Harden configuration and bounded runtime state. This addresses ignored unknown YAML fields, ambiguous decoder forms, event-driven-only sequence maintenance and insufficiently bounded deduplication. Add strict field-aware parsing, canonical-record tests, independent maintenance and explicit state limits.
  4. Make transport health measurable and broaden the evaluation matrix. This addresses diagnostic-only loss observation and the single-kernel, single-workload, three-repetition campaign. Add cumulative submission/receipt/drop/decode counters, known-volume stress tests, longer runs and representative kernels, workloads and detector sets before considering a transport replacement.
  5. Reduce deployment privilege and define the external integration boundary. This addresses the privileged, unconfined laboratory monitor and the absence of cross-node context. Derive minimum capabilities and mounts per probe family, validate a hardened node deployment, and define a versioned evidence/alert export contract for an optional external aggregator without moving cluster identity into the local detector.

Targeted hooks, contextual anomaly models and enforcement are secondary research options, not primary unfinished work. They should be mentioned only in one closing sentence, if at all, because each would require a new threat model and evaluation rather than merely completing the current prototype.

8. Forbidden Claims and Stale Terminology

  • Do not introduce an official product name or use the repository’s internal name. Use “the prototype”, “the proposed tool”, “the monitoring agent” or “the proposed system”.
  • Do not call deterministic matches “anomaly discovery”. Prefer “point detector”, “collective detector”, “bounded sequence” and “configured match”.
  • Do not use “Tracee-like” as a final architectural label. Chapter 2 already owns related-work attribution.
  • Do not describe the BPF ring buffer as current transport. The implementation uses a perf buffer.
  • Do not say that policies generate alerts or enforce actions. Policies define scope and selection; detectors evaluate admitted events and produce alerts.
  • Do not call UID 10001 a Pod, container, tenant or workload identity. It was an exact experimental admission key.
  • Do not use the stale kernel 4.18.0-553.109.1.el8_10.x86_64. The evaluated target is 4.18.0-553.137.1.el8_10.x86_64.
  • Do not reuse shared-Pod results, five-repetition benchmarks or superseded evaluation values.
  • Do not state an exact 91.97% or 92.03% reduction in the conclusion; use approximately 92.0%.
  • Do not use “overhead below 5%”. Use “monitor-container cgroup CPU below the 5% project gate”.
  • Do not say “zero lost events”. Use the authorised diagnostic wording.
  • Avoid promotional adjectives including “novel”, “innovative”, “unique”, “comprehensive”, “robust”, “scalable”, “state of the art” and “production-ready”.

Final editorial verdict. The defensible conclusion is that the thesis implemented and evaluated a selective, target-compatible, node-local runtime monitoring prototype that converts bounded kernel observations into typed evidence and deterministic local alerts. The controlled campaign supports the configured same-node cross-Pod detector and the operational value of exact early UID admission under the measured cgroup boundary. The remaining work is primarily stronger assurance, broader evaluation and safer deployment, not the first construction of the pipeline itself.

2. Concrete Problem Addressed

The thesis addresses how to build a selective, node-local runtime security monitor on the specified Rocky Linux 8 kernel. The system must collect security-relevant kernel observations, preserve a stable binary boundary, convert records into typed Go events and apply configurable policies and deterministic local detectors without requiring detection logic to be embedded in every eBPF program.

The problem is narrower than general anomaly detection or Kubernetes security analytics. It does not include enforcement, distributed correlation, learned behavioural baselines, complete ATT&CK coverage or production-readiness certification.

The reviewed sources contain a minor 91.97% versus 92.03% discrepancy caused by rounded versus unrounded inputs.

5. Implemented Contribution versus Research Novelty

The thesis can claim an implemented and evaluated engineering contribution: it combines selective eBPF collection, target-kernel compatibility, a typed Go event pipeline and configurable local detection in one coherent prototype. The reviewed literature already contains event-oriented collection, declarative rules, policy-driven tracing and runtime detection. The current related-work analysis and experiments do not establish that the architecture, policy/detector distinction or sequence-correlation model is independently novel.

Chapter 7 should therefore use formulations such as the thesis implemented, the prototype integrates and the evaluation demonstrated in the tested scenario. It should avoid novel, first, unique or equivalent priority claims unless a separate novelty argument is added.

7. Proposed Narrative for Section 7.1

Section 7.1, Summary of the Work, should contain four short paragraphs:

  1. Restate the concrete objective and target boundary: a selective node-local monitor for the specified Rocky Linux environment, not a general anomaly or enforcement platform.
  2. Summarise the kernel-space result at architectural level: complementary hooks, shared bounded records, logical-to-physical probe planning, early filtering and target-specific compatibility. Do not repeat the hook catalogue.
  3. Summarise the Go pipeline: validated bootstrap, typed decoding, policy admission, deterministic point/collective detection, bounded local correlation and ATT&CK classification. Do not repeat YAML fields or algorithms.
  4. State the contribution category explicitly: an implemented and evaluated engineering integration of established mechanisms, with clearly delimited local scope.

8. Proposed Narrative for Section 7.2

Section 7.2, Main Results, should contain three evidence-led paragraphs:

  1. Report the cross-Pod functional result: separate monitor, target and trigger Pods on one node; successful application outcome and one complete four-event alert in each of three exploit runs; no alert in three repetitions of the defined benign control.
  2. Report the operational result with its denominator: 0.46% versus 5.73% mean monitor-container cgroup CPU as a percentage of one core, approximately 92.0% lower with exact UID filtering; all filtered means below the 5% project gate.
  3. Interpret conservatively: the evidence demonstrates viability for this target and scenario, while sample size, workload, same-node topology and metric boundary prevent general claims about accuracy, total overhead or production readiness.

9. Smallest Supported Conclusion Set

  1. The thesis objective was met at prototype scope: the system provides an end-to-end node-local path from selective eBPF observations to typed Go events and configurable deterministic alerts on the stated target.
  2. The final same-node cross-Pod scenario demonstrated that the monitor could observe the target activity and complete the configured four-event sequence in all three attack repetitions, while the repeated defined benign control produced no matching alert.
  3. In the measured workload, exact UID filtering was associated with mean monitor-cgroup CPU of 0.46% of one core compared with 5.73% unfiltered, an approximately 92.0% difference, and the filtered profile satisfied the thesis's narrow 5% gate.
  4. These results support a research prototype, not claims of general detection accuracy, total-system overhead, enforcement, universal portability, cluster-wide correlation or production readiness.

10. Design Intentions and Future-Only Material

  • BPF ring-buffer transport; the implementation uses perf-event transport.
  • Cluster-wide aggregation, cross-node correlation and contextual anomaly analysis.
  • Operation blocking, response or other enforcement.
  • A least-privilege production Kubernetes deployment and a versioned orchestration package.
  • Strict rejection of unknown YAML fields and generation of the C/Go event contract from one source.
  • Generalisable accuracy, workload, kernel-version and total-system performance claims.

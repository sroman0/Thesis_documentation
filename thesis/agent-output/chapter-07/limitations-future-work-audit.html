Limitations and Future Work Audit

Prepared for Chapter 7 on 25 August 2026. Older reports and roadmap entries were checked against the current implementation and tests.

Editorial Decision

The main limitation is assurance, not absence of a working pipeline. The prototype already implements broad host-hook collection, selective loading, decoding, policy admission, point and collective detectors, bounded partial sequences, ATT&CK metadata, structured diagnostics, exact UID admission and a cross-Pod evaluation. Future work should first strengthen contract consistency, integration testing and operational evidence before expanding the feature catalogue.
Immediate baseline defect. On the inspected commit, make test-registry and the complete Go suite fail because security_socket_sendmsg is registered as a public probe but has no decoder schema. Its eBPF program updates networking support state and does not submit an independent public event. It should therefore be classified as an internal support probe, or be given a deliberate public event contract if that behaviour is intended. This correction precedes future development and should not be disguised as a long-term direction.

No more than five primary future directions are justified. Enforcement, learned contextual anomaly detection and cluster-wide correlation remain optional extensions: they would change the system boundary rather than complete the current node-local monitor.

Items Already Implemented

The following roadmap entries are stale as future work and must not be presented as missing:

  • Policy and detector YAML loading, deterministic directory ordering and event-name validation.
  • Policy-driven event selection and detector-catalogue selection.
  • Point and collective YAML detectors with compiled conditions and event-indexed dispatch.
  • Local process, immediate process_tree, device-inode resource, local cgroup and composite correlation plans.
  • A two-second default and five-second maximum collective window, periodic event-driven pruning and a 4,096-key per-detector partial-state cap.
  • Separate event, alert and Zap diagnostic paths, including perf-buffer loss warnings.
  • MITRE ATT&CK metadata propagation and policy selection by tactic or technique.
  • Exact effective-UID filtering in the shared eBPF path and its controlled performance evaluation.
  • Cross-Pod, same-node Minikube visibility and one scenario-specific collective detector evaluation.

External YAML parsing is not strict. Policy and detector loaders call yaml.Unmarshal; unknown keys are ignored. Semantic validation catches known-field errors but cannot diagnose a misspelled key that disappears during parsing. A policy or detector may load with weaker or different behaviour than the author intended. P1 Use a decoder with KnownFields(true), reject multiple documents and trailing content deliberately, and add path-aware diagnostics with typo regression tests. Engineering
Decoder acceptance is bounded but not fully canonical. Unknown IDs, invalid indexes, oversized values and truncated typed payloads are rejected. Missing arguments are tolerated, duplicate indexes overwrite earlier values, and argument-count/trailing-byte consistency is not enforced as a canonical form. Malformed records can be accepted ambiguously, making contract faults harder to distinguish from intentionally omitted fields. P1 Define canonical versus intentionally sparse records, then add duplicate-index, count-mismatch, trailing-byte and required-argument tests. Reject only cases that cannot be valid producer output. Engineering
Collective cleanup depends on relevant traffic. Each detector bounds partial keys at 4,096 and prunes on qualifying events. The engine exposes Flush, but the production runtime does not schedule it independently. Expired state can remain allocated while a detector is idle, although the hard capacity prevents unbounded sequence growth. P1 Add a low-frequency runtime maintenance tick or explicit engine lifecycle hook, with deterministic clock tests and shutdown flushing. Engineering
Alert deduplication has no independent capacity bound and uses a coarse key. Entries are time-pruned only when alert batches are processed; the key is based on detector and first evidence event rather than the complete collective sequence. High-cardinality alerts can grow the cache between pruning opportunities, and distinct collective sequences may be collapsed when their first evidence is identical. P1 Bound the cache, define eviction metrics and derive a sequence-aware fingerprint from the correlation/evidence identity. Keep deduplication separate from detection correctness. Five Primary Future Directions

  1. Generate and continuously verify the event contract. Repair the current support-probe classification, then make event IDs, schemas, probe exposure and shared layout constants derive from one source. This has the highest leverage because every hook and detector depends on the contract.
  2. Add lifecycle and target-kernel integration testing. Cover object resolution, selective autoload, map configuration, each attachment route, partial failure rollback, cancellation and cleanup. Unit-test through injected interfaces and retain a smaller privileged smoke suite on Rocky Linux.
  3. Make external configuration strict and diagnostic. Reject unknown YAML keys and ambiguous documents, report file and field paths, and extend decoder canonical-form tests so invalid configuration and invalid records fail early and clearly.
  4. Complete bounded state management. Schedule detector maintenance independently of event arrival, cap deduplication state, expose eviction/suppression metrics and use a sequence-aware fingerprint without merging deduplication with causal correlation.
  5. Harden and broaden operational validation. Expose transport-accounting metrics, stress perf-buffer delivery, investigate ring-buffer feasibility only after target-kernel verification, expand workloads/kernels/detectors, and derive a least-privilege Kubernetes profile from measured attachment needs.

Direction 5 is intentionally a staged validation programme rather than a claim that ring-buffer migration or production Kubernetes support is already selected. Metrics and privilege inventory come first; transport replacement and deployment changes require comparative evidence.

Secondary and Speculative Extensions

Targeted hook additions

Add only observation points required by a detector or missing operation stage. A complete syscall catalogue is not a security objective and would work against the measured filtering strategy.

External cluster aggregation

A central platform could combine versioned node alerts with Kubernetes inventory. This is an adjacent system, not unfinished local correlation.

Contextual anomaly detection

Learned baselines, statistical scores and cluster context require new data, evaluation and threat models. They should not be described as the natural next implementation step.

Enforcement

Blocking through LSM or other mechanisms would require safety, policy-conflict and failure-mode analysis. The current prototype is observational, so enforcement remains optional research.

Integrity reconstruction

Hidden-module discovery, handler-code inspection and complete eBPF attachment graphs are attractive but substantially exceed the evidence-preserving hooks currently implemented.

User-session correlation

user_session should remain rejected until a stable session identity enters the normalised event model. UID alone is not an acceptable approximation.

Compact Plan for Sections 7.3 and 7.4

7.3 Limitations

  1. Implementation assurance. State that C/Go contracts and registries are separately maintained, configuration parsing is not strict, and kernel-backed lifecycle coverage is limited. Mention the frozen revision's registry status only after it is repaired.
  2. State and transport boundaries. Summarise event-driven sequence cleanup, unbounded dedup cache, arrival-order correlation and diagnostic-only loss observation. Do not repeat exact algorithms from Chapter 5.
  3. Coverage and deployment. Explain that host hook coverage is selective, the monitor is observational and privileged, and local identities do not provide cross-node context.
  4. Evaluation scope. Reuse Chapter 6's final qualifications in one paragraph: one kernel, node, workload and detector; three repetitions; cgroup CPU rather than total overhead; no general accuracy or loss-free claim.

7.4 Future Work

  1. Lead with generated contract/registry consistency and integration tests as immediate engineering work.
  2. Group strict YAML, canonical decoder validation and bounded detector maintenance under runtime robustness.
  3. Describe observable transport metrics, comparative transport experiments and broader evaluation as the evidence programme.
  4. Close the primary roadmap with least-privilege Kubernetes hardening.
  5. End with one short optional paragraph on external aggregation, contextual analysis and enforcement, explicitly outside the local prototype.

Unresolved Questions

  1. Should security_socket_sendmsg remain a purely internal network-context helper, as its current eBPF implementation indicates, or is a distinct public payload planned?
  2. Which source should become authoritative for generation: a language-neutral event schema, the Go registry or a dedicated build specification?
  3. Which arguments are formally optional per event? This decision is required before the decoder can reject missing values or count mismatches safely.
  4. Can privileged object-backed integration tests run in CI on the Rocky Linux target, or must they remain a separately scheduled laboratory gate?
  5. What operational bound is acceptable for the deduplication cache, and should suppression identity include the full collective evidence or the detector correlation key?
  6. Does the target vendor kernel expose a usable backport of the BPF ring buffer? This must be probed on the exact kernel before transport migration is proposed.
  7. Which two or three additional workloads and detectors best represent the intended company deployment without turning the evaluation into an unbounded coverage study?
  8. What is the minimum privilege set for the approved hook profile, and which probes should degrade gracefully when a capability or mount is unavailable?

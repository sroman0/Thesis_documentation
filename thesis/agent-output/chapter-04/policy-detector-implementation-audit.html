2. Section 4.7.1: YAML Policy and Detector Definitions

2.1 Policy loading and conversion

Policy paths may identify individual .yaml/.yml files or directories. Directory traversal is non-recursive and filenames are sorted before loading. Each document is unmarshalled into a file-facing structure and then converted into the internal Policy, Scope, Rule, EventSelector and ArgFilter model. The runtime consumes this internal model rather than the YAML representation.

Mode and intent have defaults: an omitted mode becomes monitor, while an omitted intent becomes threat_hunting. A policy must have a name, a supported mode and intent, and at least one rule. Event include/exclude names are subsequently checked against the event registry by the command bootstrap layer. Runtime matching evaluates policy scope first and then treats rules as alternatives; constraints within one rule are conjunctive. Exclusion takes precedence within an event selector, and a matching suppress policy takes precedence over monitor or detect matches.

Argument filters are converted from compact strings beginning with args.. Equality and inequality are supported, comma-separated values provide alternatives, and a restricted leading/trailing wildcard syntax implements prefix, suffix and contains matching. This boundary is intentionally lightweight: malformed or unsupported filter strings are ignored by conversion rather than rejected as policy errors. The YAML decoder is also not configured in strict known-field mode, so Section 4.7 should not claim rejection of every unknown YAML property.

2.2 Detector schema and two-stage validation

A detector document contains stable metadata, event requirements, consumed events, optional state configuration, global conditions, ordered steps, output metadata, ATT&CK metadata and tags. Parsing converts this external schema into a Parsed representation whose Definition is independent of the YAML package. Strings are trimmed, severity is lower-cased, duplicate consumed event names are removed, and the resulting event list is sorted. When consumes is omitted, it is derived from requirements and steps.

Validation deliberately occurs in two stages:

  1. Catalogue parse stage: validates identifier and name presence, severity, time-window bounds, syntactic ATT&CK identifiers, non-empty and registered event references, and the availability and compatibility of correlation strategies.
  2. Instantiation stage: compiles global and step conditions, rejects unsupported operators or invalid numeric constants, compiles the correlation plan again into runtime components, and allocates detector-local state.
The complete catalogue is parsed before policy selection, but executable conditions are compiled only for selected detector instances. Therefore, “the complete catalogue is fully validated before selection” is too strong. A precise claim is that every catalogue entry undergoes structural, metadata, event-reference and correlation validation before selection, while condition compilation belongs to selected-detector construction.

The step alias field as is preserved by the parser but is not used by the current evaluator. Optional event requirements are represented in metadata, but Definition.EventNames() includes optional and mandatory requirements alike for dispatch and selector event-coverage checks. This should not be described as optional runtime enrichment with separate execution semantics.

3. Bootstrap Admission and Detector Catalogue Selection

3.1 Event-scope compilation

The policy manager can derive an exact event allow-list only when every non-suppressive rule has a non-empty include list. The union of those explicit includes is intersected with an operator-supplied event list. This result is applied before the eBPF runtime selects and attaches probes. If any relevant rule is open-ended, the manager returns no exact restriction and the wider requested collection scope is preserved.

After decoding, events still pass the ordinary event-name and command filters and then the policy manager. With no configured policies the policy boundary is permissive. With policies, an event proceeds only if at least one policy matches and none of the matching policies suppresses it. A rejected event reaches neither raw-event presentation nor detector dispatch. The alerts-only option suppresses raw presentation after admission but does not remove the event from detector processing.

3.2 Policy-driven detector selection in the dirty working tree

The audited changes add a detector selector to non-suppress policies. Criteria may refer to detector IDs, severities, ATT&CK tactics, ATT&CK techniques, tags and statefulness. Values inside one criterion field use OR semantics; different non-empty fields use AND semantics. Include criteria identify candidates, then matching exclude criteria remove candidates for that policy. Selections from separate policies are combined by union, so exclusion is policy-local rather than a global veto.

Selector values are normalised at load time: severities and tags are lower-cased, tactics and techniques are upper-cased, and surrounding whitespace is removed. Matching against detector IDs, tags and metadata is otherwise exact. Duplicate selector values, unsupported severities and malformed ATT&CK ID shapes are rejected. Explicit unknown detector IDs and selectors that match no available definition are bootstrap errors.

For each detector selected by a policy, the implementation verifies that the same policy's event rules match every name returned by the detector definition. This is broader than mandatory requirements alone: it covers consumed events and optional requirements as well. Scope, command, UID and argument predicates do not participate in this bootstrap coverage check. The check establishes declared event availability, not that every admitted runtime event will satisfy narrower policy predicates.

All detector files are parsed first. Selection is then applied to their definitions, and only selected entries are instantiated and inserted into the engine. If no policy contains a selector, legacy behaviour loads the full catalogue. If at least one selector exists, policies without selectors do not independently restore the full catalogue. If policies request detector selection but no detector path is configured, the runtime leaves the detector layer disabled and emits a warning rather than failing startup.

4. Section 4.7.2: Runtime Registry, Dispatch and Detection

4.1 Registry and lifecycle

The engine constructs a registry from selected detector instances. Registration rejects nil detectors, invalid definitions and duplicate IDs, and stores detectors in deterministic ID order. A separate dispatcher builds an event-name index once. Detectors declaring no event names are treated as wildcard consumers; all others are invoked only for indexed event names. This keeps event-time dispatch proportional to interested detector instances rather than the whole registry.

Engine initialisation invokes every detector and joins initialisation failures into a startup error. During event processing, an error from one detector is returned with that detector's ID and does not prevent other candidates from running. The engine records counts for processed events, candidates, invocations, skipped detectors, emitted and suppressed alerts, flushes and errors. The field named DetectorMatched currently counts dispatch candidates, not successful condition matches, and should be described accordingly.

The API permits registration after initialisation and rebuilds the dispatch index, but the newly registered detector is not automatically initialised. The production bootstrap constructs the complete engine before calling initialisation, so dynamic post-start registration is not part of the current operating path.

4.2 Compiled deterministic conditions

Detector conditions are compiled once during selected-detector construction. The compiler normalises field and operator names, pre-splits membership lists and parses numeric constants before events enter the hot path. Runtime evaluation resolves fields from the common event context or typed arguments and applies the compiled operator. Supported operators are equality, inequality, substring containment, exact membership, prefix, suffix, existence, non-existence, greater-than and less-than.

Global conditions must all match. For a point detector, a matching consumed event produces an alert immediately. A non-stateful definition containing several steps treats those steps as alternative event-specific condition sets rather than as a sequence. A detector is handled as collective only when it is marked stateful and contains more than one compiled step.

4.3 Collective state transitions and evidence

For a collective detector, every admitted candidate first passes global conditions. Correlation keys are then calculated. If a key identifies an existing partial sequence, the event is compared with the next expected step. A match appends the full decoded event to retained evidence and advances the step index. Completing the final step removes the partial state and emits one alert containing the ordered event slice.

If no existing state advances and the event satisfies the first step, the detector starts a new partial sequence. Starting again under the same key replaces the previous incomplete sequence, resets its first-seen time and discards its previous evidence. One detector therefore stores at most one partial sequence per key. Events that match neither the expected next step nor the first step leave existing unexpired state unchanged.

Point alerts retain one decoded source event. Collective alerts retain each event that advanced the sequence, in arrival order. The detector adds metadata identifying the YAML source, the first event name and event count; it does not add the names of policies that admitted or selected it.

5. Section 4.7.3: Correlation, Bounds, Flush and Deduplication

5.1 Exact correlation semantics

StrategyRuntime identityExact boundary
process Host PID and process start time. Both values must be non-zero. Combining them prevents a reused numeric PID from joining a previous process lifetime. Legacy PID spellings are normalised to this strategy.
process_tree Current host PID/start time, with immediate host parent PID/parent start time as an additional lookup candidate. The first step is stored under the current process identity. Later events may match in the same process or in an immediate child. There is no persistent process graph and no arbitrary ancestry traversal.
resource Typed dev and inode event arguments. Every sequence step must have both arguments in the registered event schema. Missing runtime values produce no key. Pathname is neither part of the key nor a fallback. Different processes may correlate through the same file object.
cgroup Non-zero event-context cgroup ID. The identity is local to the monitored node. It is not a pod, container or cluster-wide workload identity.
Composite An ordered conjunction of two or more supported components. Every component must produce a value and agree. For process_tree, current and immediate-parent candidates are combined with all other configured dimensions.

An omitted group_by defaults to process. Unknown strategies, duplicate strategies after alias normalisation and user_session are rejected. The latter is deliberately unavailable because UID is an account identity rather than a stable login-session identity.

Runtime flush qualification. No production call site currently schedules Engine.Flush. Normal cleanup is therefore driven by later relevant detector events. An idle detector may retain expired entries until another matching event arrives or an external caller explicitly invokes the flush API. Chapter 4 must distinguish the implemented flush capability from the behaviour of the current main runtime loop.

5.3 Post-detection alert deduplication

Deduplication is an engine-level stage after all candidate detectors have evaluated an event and before alerts are returned to the output path. It does not suppress raw events and does not alter detector sequence state. The default interval is 5 seconds. A repeated alert is suppressed when the elapsed time since the same key was last emitted is strictly less than that interval.

The key contains detector ID, title and severity plus the first evidence event's event name, process PID, UID, command and ordered arguments. Timestamps and thread IDs are omitted. For collective alerts, later evidence events are not part of the key. Consequently, two distinct collective completions that share the same first event and alert metadata may collapse inside the deduplication window. Deduplication state is pruned when a non-empty alert batch is processed, using twice the configured interval as the retention threshold.

6. Section 4.7.4: MITRE ATT&CK Metadata

Detector YAML may declare a framework label, version, tactics, techniques, data sources and data components. Parsing trims these fields and transfers them into the internal detector definition. Validation checks only the syntactic shape of non-empty tactic IDs (TA followed by four digits) and technique IDs (T followed by four digits, optionally followed by a three-digit sub-technique suffix). Empty mappings are valid.

The runtime does not load an ATT&CK catalogue, verify names against IDs, validate framework versions, assess semantic correctness or demonstrate technique coverage. In the audited dirty working tree, policy selectors can use tactic and technique IDs as exact bootstrap metadata criteria. When a detector matches, its complete threat metadata is copied into the alert alongside retained evidence. The output layer later renders a compact table summary or structured JSON; those presentation mechanics belong in Section 4.8.

Policy names and selector provenance are not propagated by the current YAML detector implementation. Although the output model can extract policy names if arbitrary alert metadata contains policy or policy_names, generated YAML alerts currently provide only source, first-event and event-count metadata. Section 4.7 must not claim end-to-end policy provenance in alerts.

7. Verified Limits and Unsupported Behaviour

  • No machine learning, learned baseline, statistical scoring or general anomaly discovery.
  • No contextual or cluster-wide correlation and no Kubernetes workload identity.
  • No arbitrary process ancestry or persistent process graph.
  • No user-session correlation and no UID-based approximation of it.
  • No enforcement or detector-driven change to kernel instrumentation after startup.
  • No general-purpose complex-event processing, event reordering or reconstruction of a total order across perf-buffer CPUs.
  • No semantic ATT&CK catalogue validation or proof of detector correctness and coverage.
  • No policy provenance in generated detector alerts.
  • No periodic engine flush in the current production event loop.
  • No strict rejection of every unknown YAML field or malformed compact policy argument filter.
  • Only one incomplete collective sequence is retained per detector and correlation key.

Documentation qualifications discovered by the audit

  • documentation/implementation/correlation.md correctly describes explicit flush cleanup but does not say that the production runtime currently has no flush scheduler.
  • documentation/implementation/output.md describes support for extracting policy names from arbitrary alert metadata. The YAML detector does not currently populate that metadata, so policy provenance is not present in ordinary generated alerts.
  • Chapter 3 states that the complete detector catalogue is parsed and validated before selection. Section 4.7 should qualify this by separating catalogue-level validation from selected-detector condition compilation.
  • Chapter 3 already owns the full architecture of policy event scope, selected detector catalogues, indexed dispatch, correlation and ATT&CK flow. Chapter 4 should avoid repeating this narrative and instead expose concrete representations, state transitions, bounds and failure behaviour.

10. Recommended Section 4.7 Emphasis

The implementation narrative should follow one concrete transition: external policy and detector documents are converted into validated internal definitions; bootstrap compiles exact event scope and, in the current working tree, selects detector definitions; selected conditions and correlation plans are compiled into detector instances; the registry and event index route admitted decoded events; point or bounded collective evaluation produces evidence-bearing alerts; the engine then applies short post-detection deduplication; and detector-owned ATT&CK metadata remains attached to the alert boundary.

This sequence is sufficiently concrete for an implementation chapter without repeating the conceptual architecture from Chapter 3. The most important implementation-specific claims are the two-stage validation boundary, policy-local selector composition, exact correlation identities, one-state-per-key replacement, the 2/5-second and 4096-state guardrails, opportunistic rather than scheduled cleanup, first-evidence-based deduplication, and syntactic rather than semantic ATT&CK validation.

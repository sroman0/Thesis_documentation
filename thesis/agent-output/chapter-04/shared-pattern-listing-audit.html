2. Shared Mechanism Audit

MechanismCommitted implementationArchitectural meaningQualification
Common initialisation and deferred enrichment init_program_data acquires the per-CPU event workspace and singleton configuration, resets arguments, records minimal identity and timing fields, and resolves task/process state. events_perf_submit refreshes the complete task context and optionally captures a user stack before transport. Hook bodies supply only event-specific evidence; shared context construction and final submission remain centralised. “Deferred enrichment” does not mean that initialisation is cheap or empty. It already performs map lookups, task-state setup, cgroup handling and policy-map work. Only the final full task-context refresh and optional stack capture are deferred.
Exact UID admission The common initialiser reads config_map[0] and invokes should_drop_by_kernel_uid_filter before argument reset and most event construction. The low 32 bits of bpf_get_current_uid_gid are compared with one configured UID. One verifier-simple equality guard applies uniformly to hooks using the common framework. It is an exact effective-UID filter, not a policy compiler, range, exclusion set, namespace-aware identity rule or authorisation mechanism.
Direct versus entry/return construction Direct hooks initialise, serialise and submit in one invocation. Paired hooks store up to seven argument slots in args_map under a key composed of logical event ID and current host thread ID; the return path loads, deletes and completes the record. The mechanism preserves request arguments until a return value is available while allowing several logical operations from one thread to occupy distinct keys. BPF_ANY replaces stale state. A missing entry causes the return-side logical event to be skipped. This is bounded temporary correlation, not a general process history.
Indexed argument serialisation Each argument begins with a one-byte schema index. Scalars use a schema-defined fixed width; variable records add bounded size or count fields. Writers update the offset and argument count only after successful writes. An omitted argument does not shift the identity of later arguments, and the wire record need not carry names or type tags. The index is meaningful only with the Go event schema. Type compatibility cannot be checked independently from the wire because no type tag is transmitted.
Explicit bounds and long records save_to_submit_buf preserves the checked offset and exposes its upper bound with update_min. Commit 163ad724a65ec8c701dc816fe87f174eeec51275 removed mask-based handling of the non-power-of-two 32,000-byte buffer and added a long-record regression test. Verifier evidence is expressed without modifying a valid write position. The regression proves the constructed long record decodes correctly; it is not an exhaustive proof for every serialiser and maximum-sized combination.
Perf-event submission events_perf_submit computes sizeof(event_context_t) + 1 + offset, clamps it to the maximum in verifier-visible form, and calls bpf_perf_event_output on the current CPU. Go consumes the events perf-event array with one libbpfgo reader. Only the used portion of the large workspace crosses the kernel/user boundary. There is no active BPF ring-buffer alternative. Per-CPU ordering and loss semantics belong to Chapter 3 and evaluation, not repeated implementation prose.
Dependency expansion and selective autoload Select resolves selected public logical events to direct producers and specifications whose impliedBy triggers match. ConfigureAutoload disables unrelated registered programs before object loading; Attach selects the libbpfgo API by probe kind. Logical selection controls a physical program plan without embedding naming rules in the loader. The guarantee covers registered programs only. Registry omissions cannot be disabled or attached by this mechanism.
Event/probe registry consistency The event registry owns numeric IDs, public names and ordered argument schemas. The probe registry owns program names, hooks, attachment kinds and dependencies. Tests cover public decoder availability, public production, internal hiding, multi-probe families and implied dependencies. The two registries define the semantic and production halves of one logical interface. There is no automated comparison of Go IDs with the C event enum. The dirty internal-flag repair described above is also needed for the current consistency suite to represent the intended committed baseline.
Schema-directed decoding DecodeEvent reads the 136-byte context and count, resolves the event ID, and decodes indexed records using the selected schema. A temporary index map is emitted in schema order as bufferdecoder.Event. The decoder is the normalisation boundary consumed directly by policies and detectors; the output model is presentation-only. Unknown IDs, invalid indexes, truncation, oversized variable fields and invalid text are rejected. Missing arguments and duplicate indexes are accepted, the later duplicate wins, and trailing bytes need not be consumed.

Listings Explicitly Excluded

  • Individual hook bodies: they create a catalogue and repeat the shared framework.
  • The complete event or probe registry: large declarative catalogues belong in generated documentation or an appendix table.
  • Generated BPF skeletons or generated headers.
  • Networking programs and packet parsing.
  • The uncommitted detector-selector implementation.
  • Output formatting and Zap setup: prose is sufficient and these mechanisms are not part of hook construction.
  • Map declarations without an algorithmic operation: they duplicate prose and expose layout detail without explaining control flow.

7. Editorial Guidance for the Revised 4.2

  1. Open with the shared construction framework and its two execution forms: direct and paired.
  2. Use the two 4.2 listings once; every later hook family refers to those patterns.
  3. For each family, explain observation stage, event-specific evidence and implementation-specific compatibility only.
  4. Do not enumerate every scalar field or reproduce registry catalogues. A complete hook-to-event matrix is an appendix candidate.
  5. When similar hooks represent different stages, contrast their semantics in one paragraph rather than repeating their common initialisation and submission.
  6. Keep all performance claims and measured effects out of Chapter 4; describe only the implemented control path.

8. Appendix Candidates

  • A generated host-hook catalogue with logical event, physical programs, attach kind, kernel symbol, direct/paired construction, observation stage and schema.
  • The complete 136-byte C/Go context field table and all argument encoding variants.
  • Detailed malformed-record acceptance/rejection cases and their test coverage.
  • Target-kernel compatibility branches and fixed verifier limits by helper.
  • The public/internal registry consistency obligations, including the remaining C/Go numeric-ID test gap.

9. Acceptance Conditions for the Writer

  • No more than seven approved listings are expected; eight is an absolute maximum.
  • Each listing is 8-18 lines unless the editorial synthesis records a justified exception.
  • Every listing replaces prose, and its surrounding paragraph explains architecture rather than individual statements.
  • The revised chapter uses committed host-hook behaviour as its factual baseline.
  • Networking and uncommitted detector selection are absent.
  • The UID listing is owned by 4.6, while the common construction and paired-retention listings are owned by 4.2.
  • Cross-references replace repeated descriptions of the record, registry, decoder and transport mechanisms.

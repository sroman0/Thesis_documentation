2. Section 4.1 — Build Toolchain and Project Organization

2.1 Implemented build graph

libbpf source submodule
  -> static libbpf archive, headers and pkg-config metadata under dist/libbpf

project.bpf.c + local headers + libbpf headers
  -> clang -O2 -g -target bpf -D__TARGET_ARCH_x86
  -> dist/project.bpf.o

dist/project.bpf.o
  -> Go //go:embed input
  -> CGO build of cmd/project with local libbpfgo bindings
  -> dist/project

make all is the canonical aggregate target. The Makefile first builds a static libbpf archive from the checked-out third-party source, installs its headers and rewrites the generated pkg-config metadata to point at the local build directories. Clang then compiles the single eBPF translation unit for x86-64, with every header under pkg/ebpf/c registered as a prerequisite. Finally, the Go entry point is built with CGO, the locally generated libbpf flags and the local libbpfgo replacement declared in go.mod.

The build ordering is functionally important: embedded-ebpf.go embeds dist/project.bpf.o, so the object must exist before the Go compiler processes the package. The resulting executable is therefore self-contained with respect to the eBPF object, although it remains a dynamically linked Linux executable because the Go runtime uses CGO and libbpf depends on system libraries.

The current module declares Go 1.22. The container builder enforces this through golang:1.22-bookworm. A locally inspected dist/project had instead been produced by the host's Go 1.26 toolchain and was marked dirty; it is evidence about that local artefact, not about the Docker build and not a version requirement to state in the thesis.

2.3 Embedded and external object handling

The common path uses the object embedded at build time. At startup, object resolution follows an explicit precedence order: the PROJECT_BPF_OBJECT environment variable, the CLI/configuration path normally supplied through --bpf-object, and finally the embedded dist/project.bpf.o. External paths are converted to absolute paths and read into memory. Relative names are also searched under pkg/ebpf/c. In both cases the loader receives object bytes, while a real or synthetic path supplies a stable object name for libbpf diagnostics.

BTF resolution is separate: PROJECT_BTF_FILE takes precedence over the CLI/configuration value, whose default is /sys/kernel/btf/vmlinux. Embedding the eBPF object does not embed the running kernel's BTF and does not remove the requirement for a compatible host kernel.

Safe thesis claim. The executable embeds its default eBPF object while retaining an explicit override for development and compatibility testing. Do not call the executable fully static or independent of the host: loading still requires BTF, kernel capabilities, privileges and dynamic user-space libraries.

3. Section 4.8 — Output and Structured Logging

3.1 Three separate result classes

The implementation preserves three independent concerns:

ClassImplementationDestinationConfiguration
Monitored eventspkg/output printer selected for decoded events.stdout--output json|table
Detector alertsA separately constructed pkg/output printer receives completed alerts.stdout--alerts, --alerts-only, --alerts-output json|table
Operational diagnosticsZap logger plus mapped libbpf callbacks.stderr--log-level and --log-format console|json

The same printer interface supports events and alerts, but the runtime creates independent printer instances so their formats can differ. --alerts-only suppresses only raw event presentation; it does not remove admitted events from detector evaluation. Zap does not serialise either monitored events or alerts.

3.2 Event presentation

The JSON printer emits one object per line. Before serialisation, it adapts the decoder model into an output-specific record that groups process, host and kernel metadata, converts fixed-size C strings, retains typed argument values and can attach symbolic labels. This is a presentation model; it must not be described as a second normalisation stage consumed by policies and detectors, because those components receive the decoded event directly.

The table printer emits one compact line containing event identity, process identifiers, user identity, command name and formatted arguments. Its semantic formatting resolves selected capabilities, signals, operations, bit masks, return values and error numbers while preserving underlying numeric meaning. JSON remains the machine-oriented form; table output is intended for interactive inspection.

The current committed networking integration adds a JSON-specific enrichment adapter. Network packet records can be replaced with decoded protocol fields and DNS-derived labels before normal JSON rendering, while socket address arguments can be expanded into filterable address fields. This should be mentioned only briefly in 4.8 because the networking implementation is outside the process/security focus and should not displace the general output architecture.

3.3 Alert presentation

The alert output record contains detector identity, title, severity, creation time, policy names, retained event evidence, metadata and an optional structured threat block. Evidence events use the same output-facing event representation as ordinary JSON events. MITRE ATT&CK data remain structured in JSON, whereas table output uses a compact identifier summary.

For a point alert, table output adds a concise source-event summary. For a collective alert, it emits the ordered evidence sequence and avoids duplicating the first event in separate source fields. The sequence string is bounded to 1,024 characters plus an ellipsis. Deduplication and correlation do not belong to the printer and must remain in Section 4.7.

3.4 Zap and libbpf diagnostics

pkg/logging creates a production-style Zap logger with console or JSON encoding and debug, info, warn or error thresholds. It writes to stderr, disables caller and stack-trace fields, uses ISO-8601 timestamps and lower-case levels, and is reserved for runtime diagnostics. Startup state, selected runtime extensions, attachment diagnostics, transport loss, decoding failures, detector failures, output errors and cleanup conditions use this path.

Libbpf supplies its own message and numeric level through callbacks. The integration attaches a source=libbpf field, maps libbpf warnings to Zap warnings and maps the remaining admitted messages to Zap debug records. Callback filtering and the Zap threshold together keep CO-RE relocation detail available at debug level while normal operation remains readable.

Some configuration and bootstrap errors occur before the managed Zap logger exists. Cobra returns these errors to the process entry point, which writes a concise error to stderr and exits non-zero. This is an outer error boundary, not a fourth monitoring stream.

4. Section 4.9 — Containerization and Deployment Considerations

4.1 Implemented image build

The Dockerfile has two stages:

  1. The builder stage uses Go 1.22 on Debian Bookworm, installs Clang, LLVM, GCC, libelf and zlib development packages, copies the complete source tree and initialised third-party sources, downloads Go modules and executes make all.
  2. The runtime stage uses Debian Bookworm slim, installs runtime libelf and zlib packages, copies the compiled executable to /usr/local/bin/project, and includes the default policy and detector rule catalogue required by the YAML-driven runtime.

The eBPF object is not copied as a separate runtime artefact because it is embedded in the executable. The build context excludes local dist and *.bpf.o files, forcing the image build to regenerate them. The local replace directive for libbpfgo means the third-party submodules must already be initialised before Docker receives the context.

Rule packaging resolved. The runtime packaging now makes the policy and detector rule catalogue available to the running container. YAML-driven monitoring can therefore be configured from the packaged rule directories without requiring a derivative image. External mounts may still be used to replace or extend those definitions operationally, but they are no longer required merely to access the default catalogue.

4.2 Host integration requirements

The container shares the host kernel. The resolved docker-run workflow starts it with --privileged, host PID and cgroup namespaces, and the host BTF, tracing/debug and bpffs resources required by the selected probes. These are operational requirements of the current demonstration workflow, not proof that least-privilege deployment has been established.

Runtime mount integration resolved. The container launch workflow has been aligned with the declared runtime mount set. Host BTF, tracefs or debugfs as required by the host layout, and bpffs are now exposed consistently to the monitoring process. Chapter 4 may describe this as the implemented Docker integration, while still noting that the container operates against the host kernel and requires privileged access in the current deployment model.
Docker documentation aligned. The obsolete development-stage description identified by the initial audit has been removed or reconciled with the supported builder/runtime workflow. Chapter 4 should document only the current image build and runtime commands, without reintroducing superseded dev-stage assumptions.

4.3 Containerization versus Kubernetes

The implemented contribution is a multi-stage container image and a privileged host-integrated demonstration command. There are no audited Kubernetes manifests, DaemonSet definitions, security contexts, volume declarations, rollout controls or cluster-level validation in the requested implementation scope. A future platform may run one monitoring agent per selected node and aggregate its output, but that is an intended integration direction rather than an implemented or evaluated thesis result.

Recommended boundary wording: “The prototype is packaged as a container image that executes against the host kernel. Integration with a Kubernetes deployment and a cluster-wide analysis platform remains outside the implemented and evaluated scope.”

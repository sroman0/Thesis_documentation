4.3 Loader, probe registry and attachment lifecycle

Concrete lifecycle

  1. Cobra writes command-line values into one central configuration object. Normalisation derives detector and alert toggles, and validation checks output and logging formats.
  2. The bootstrap resolves the eBPF object from an environment override, an explicit path, or the embedded dist/project.bpf.o. BTF is resolved from an environment override, the configuration, or /sys/kernel/btf/vmlinux.
  3. Policies are loaded before runtime construction. When their event selectors form a finite allowlist, that allowlist is intersected with the operator's requested events and becomes the effective event selection. Open-ended policy scope does not narrow attachment.
  4. The probe registry translates logical event names into one or more attachable program specifications and adds internal dependencies implied by selected public events.
  5. The runtime opens the object through libbpf, disables autoload for registered but unselected programs, and invokes object loading. CO-RE relocation and verifier checks therefore apply only to registered programs that remain enabled, subject to the limitation below.
  6. After loading, userspace writes the optional UID filter into config_map, creates and starts the events perf reader, initialises the event gate map used by current networking work, and attaches each selected program with the API dictated by its probe kind.
  7. The run loop consumes perf records until cancellation. Shutdown destroys links in reverse order, releases any runtime-managed cgroup-v2 mount, closes the perf reader, and finally closes the module.

Selective autoload is registry-bounded. It disables only programs represented by the probe registry. It is not evidence that every program present in the compiled object is covered. Registry completeness is therefore part of the loader's correctness boundary.

Public producers and internal support probes

A public probe specification belongs to the user-facing event API: its logical name can be selected through the CLI, appears in the event list, and normally has a decoder schema. An internal specification is attachable implementation support but is hidden from user selection because it does not define a stable standalone event payload. The impliedBy relation lets selection of a public event activate these support programs automatically.

The mapping is not one-to-one. Several programs can produce one logical event, as with entry/return syscall families such as open, chmod, chown, and ptrace. Conversely, the cgroup packet-direction selectors produce protocol-specific network records rather than records named after the attach direction. These are deliberate exceptions encoded in registry tests.

Attachment strategies

The registry selects among raw tracepoints, tracepoints, kprobes, kretprobes, and cgroup skb ingress or egress attachments. Tracepoint category and name are parsed from the registered hook string. Cgroup programs require a resolved cgroup-v2 mount; other probe kinds attach directly to the registered kernel hook.

4.4 Binary event contract and kernel transport

Record structure

All ordinary events use one variable-length record:

[event_context_t: 136 bytes][argument count: uint8][indexed argument records]

The common context carries the timestamp; process, thread and parent identities in namespace and host views; effective UID; cgroup and namespace identifiers; command and UTS names; process start-time identities; event ID; associated syscall; stack identifier; CPU identifier; and reserved policy metadata. The Go EventContext mirrors this order and fixes the decoder boundary at 136 bytes.

The kernel event object embeds the common context and an argument buffer. Each captured argument begins with a one-byte schema index. Scalar values then occupy their fixed-width payload; strings and byte arrays add a four-byte length; string arrays and compact argument arrays use their own bounded headers. The schema index, rather than emission order alone, allows userspace to restore the declaration order and tolerate arguments that a hook could not capture.

Submission path

Common event initialisation first obtains the per-CPU event workspace and the singleton configuration entry. The minimal UID guard runs before argument reset, context enrichment, and submission. A hook then captures only its event-specific arguments. At submission time the common helper enriches the task context, optionally records a user stack identifier, computes the exact record length from the fixed context, count byte and current argument offset, and calls bpf_perf_event_output for the current CPU.

Long-record offset correction

Commit 163ad724a65ec8c701dc816fe87f174eeec51275 corrected a kernel-side offset defect. The 32,000-byte argument buffer is not a power of two, so applying offset & (ARGS_BUF_SIZE - 1) did not merely prove a verifier bound: it folded valid offsets onto earlier positions and could overwrite long records. The corrected helper preserves the checked offset and communicates its upper bound to older verifiers with an explicit bound operation. The write of the argument index now uses that preserved offset.

The regression test builds a security_bprm_check record whose argument region exceeds 256 bytes and verifies that both long strings and subsequent scalar arguments decode correctly. This demonstrates the userspace-visible symptom is fixed for the constructed record. It is not a full proof for every argument helper or maximum-size record.

4.5 User-space decoder and event registry

Decoding sequence

The decoder reads the 136-byte context field by field using little-endian scalar operations, reads the argument count, resolves the numeric event ID through the event registry, and processes the remaining bytes as indexed argument records. For a known event, the index selects the registered argument name and decoding type. Successfully decoded arguments are returned in schema order in a bufferdecoder.Event containing the common context, logical event name, and typed values. This is the structure consumed by the later policy and detector stages; presentation may adapt it further, but there is no second security-event normalisation object between decoding and those stages.

Event and probe registries

The event registry is authoritative for semantic decoding: it maps an ID to a public name and ordered argument schema, and provides reverse name lookup. The probe registry is authoritative for production and attachment: it maps public logical events and internal dependencies to compiled program names, hooks, and attachment kinds. Neither registry replaces the other.

Tests enforce sorted unique public names, ID/name round trips inside the Go event registry, decoder coverage for ordinary public probes, public exposure for ordinary decoder events, and exclusion of internal probes from CLI selection. They also exercise multi-probe logical events and implied dependencies. Two qualifications are necessary: network direction selectors are explicit exceptions to the one-public-probe/one-decoder-name rule, and no automated test was found that compares Go event ID constants directly against the C enum values. The C/Go numeric-ID contract therefore still depends on disciplined synchronized maintenance.

4.6 Event selection and kernel-side filtering

Four distinct controls must not be conflated. Probe selection decides what can be produced; event admission decides whether a decoded record continues; output suppression decides whether that admitted record is printed; detector dispatch decides whether the admitted record is evaluated by the detector engine.

UID configuration-map contract

The singleton array map config_map stores config_entry_t at key zero. Userspace reads the existing value, checks that it is large enough, and patches little-endian fields at byte offset 12 for the 16-bit enable flag and byte offset 16 for the 32-bit UID. These offsets correspond to three initial 32-bit fields, followed by the enable flag, the 16-bit policy version, and the UID. The whole C structure is deliberately not mirrored in Go because most of it belongs to broader policy configuration.

The kernel compares the low 32 bits returned by bpf_get_current_uid_gid, i.e. the current effective UID, with the configured exact UID. A null configuration or disabled flag admits the event. This is a single-value equality filter, not a UID range, exclusion set, namespace-aware identity rule, or general policy compiler.

At present there is no dedicated Go unit test for the raw byte offsets or an integration test that reads the map back from a loaded object. The offsets are supported by direct C-layout inspection and runtime documentation, so Chapter 4 should present them as an implemented ABI obligation rather than as a self-verifying contract.

4.2 eBPF Program Implementation

Common Implementation Framework

The programs share one event-construction framework rather than defining a separate wire format for each hook. A fixed event context carries the timestamp, process and namespace identifiers, effective UID, command name, UTS name, event and syscall identifiers, CPU, stack identifier, and policy metadata. This context is followed by a compact argument area. Arguments are indexed and serialised according to the schema associated with the logical event; variable-length values additionally carry their encoded size.

The event context, argument buffer, task state and temporary path data are intentionally allocated in maps. The principal event object is held in a single-entry per-CPU array, while a second per-CPU scratch map provides two reusable work areas. This avoids placing large structures on the restricted BPF stack and removes cross-CPU contention during event construction. LRU hash maps retain bounded task and process state, and a separate hash map stores arguments that must survive from an entry probe to a corresponding return probe.

Every normal event follows the same preparation sequence. The common initialiser obtains the per-CPU event object and global configuration, applies the optional exact effective-UID filter, clears the previous argument state, records minimal event metadata, and obtains the cached task and process state. Full task-context enrichment is deferred until an event is actually submitted. This ordering allows a rejected UID to return before path resolution, argument copying, context enrichment, and transport submission.

The active submission path uses a perf-event array. Immediately before submission, it refreshes the task context, optionally captures a user stack, calculates the exact record length from the fixed context and the used argument bytes, constrains that length for the verifier, and emits the record on the current CPU. Ring-buffer helper structures remain in the source tree for portability, but they are not the active event transport and should not be described as such in Chapter 4.

Argument Buffer and Bounded Serialisation

The argument area has a capacity of 32,000 bytes and accepts at most 32 indexed arguments. Fixed-width values are written directly after their index. Strings and other variable-length values contain an index, an explicit length, and their payload. Per-argument offsets are retained so that selected string values can also be consulted by in-kernel filtering logic. String arrays are traversed with a compile-time bound, accept at most 38 elements, and append a truncation marker when the source array exceeds that limit.

All write helpers check both the current offset and the requested write size. This is particularly important because the argument-buffer capacity is not a power of two. Commit 163ad724a65ec8c701dc816fe87f174eeec51275 replaced an invalid bit-mask normalisation with an explicit bounds check. The former mask could fold offsets once a record exceeded 256 bytes and corrupt argument positions. A decoder regression test now exercises a security_bprm_check record whose later arguments lie beyond that boundary.

4.2.1 Process Lifecycle and Execution Hooks

Process execution is represented through complementary stages rather than a single all-purpose probe. The execve and execveat syscall-entry programs record execution attempts and copy the pathname and bounded argument vector while user memory is still available. The security_bprm_check and security_bprm_creds_for_exec probes observe later security checkpoints and can report the resolved executable and credential-related data. The scheduler execution tracepoint reports the successful replacement of the process image. A paired entry/return implementation emits process_execute_failed only when the syscall return value is negative.

This division preserves distinct semantics: an attempted path, a security decision point, a successful image transition, and a failed transition are not collapsed into one event. Fork, exit and task-renaming tracepoints use the same common context and submission machinery but require no entry/return state.

4.2.2 Credentials and Privilege Hooks

The credential hooks use two recurring patterns. First, security_task_fix_setuid observes the LSM mediation stage and compares the old and proposed credentials. It emits real, effective, saved and filesystem user identifiers together with the operation flag, and suppresses requests that produce no relevant change. This is an entry-only observation: it describes the proposed transition and does not assert the final syscall result.

Second, the commit_creds probe compares the current real credential object with the replacement credential object. When a change is present, it serialises a compact, layout-stable credential snapshot containing user and group identifiers and capability sets. Dedicated syscall entry/return pairs complement these hooks by retaining the requested identifiers and appending the syscall result. The two views therefore distinguish security mediation, committed kernel credential state, and user-visible syscall completion.

4.2.3 Filesystem, Memory and Namespace Hooks

security_file_open demonstrates filesystem enrichment at a security hook. It reconstructs the resolved kernel path and reports file flags, device, inode and change time, while also retaining the original pathname obtained from the active syscall registers. Path reconstruction uses a per-CPU buffer, follows mount transitions, recognises disconnected dentries, and stops after 20 components. The dedicated open event, by contrast, correlates the open and openat syscall entry and return tracepoints so that the requested pathname, flags, mode and resulting file descriptor or error remain in one logical record.

The same entry/return design is reused for permission and ownership changes. Multiple syscall variants, such as chmod, fchmod and fchmodat, produce one logical chmod event, while their operation field preserves the originating variant. Memory operations use typed syscall tracepoints suited to the target kernel. Their exit programs append the return value, while process-to-process memory events intentionally retain vector metadata rather than copying arbitrary transferred payloads.

Namespace monitoring combines request-level and state-level observations. The setns and unshare events retain syscall arguments until completion and include the result. The switch_task_namespaces probe compares the old and new namespace identifiers and emits only when a relevant identifier changes. This avoids representing a no-op namespace assignment as a transition.

4.2.4 Kernel Integrity and eBPF Activity Hooks

Kernel-integrity coverage combines high-signal entry probes with paired functions whose outcome is important. The security mediation hooks for BPF commands, maps and programs report compact command or object metadata without attempting to duplicate every attribute passed to the syscall. Module tracepoints report module identity, while the paired do_init_module probes preserve the final initialisation result. The same temporary-state mechanism correlates entry and return for kprobe registration and kernel-symbol lookup, making the requested symbol and resulting status or address available in one event.

Additional entry-only probes observe creation of procfs interfaces and user-mode helper invocation. These are observations of security-relevant kernel activity, not hidden-module detection or active enforcement. The current implementation does not reconstruct arbitrary kernel tampering, detect every concealed module, or deny the observed operation.

4.10 Compatibility and Verifier Challenges

CO-RE Reads and Explicit Compatibility Branches

CO-RE is used for kernel structure reads, but the implementation does not assume that relocation alone resolves semantic changes between kernel generations. It combines relocatable field access with explicit type, field and helper-existence branches. The resulting object remains tied to the hooks, helpers and verifier behaviour actually supplied by the target kernel.

Verifier-driven Limits and Target Workarounds

  • Large event, path and scratch structures reside in maps rather than on the BPF stack.
  • Path walks, string arrays and other traversals have fixed upper bounds and use unrolled loops where required.
  • Buffer helpers repeat explicit bounds checks after helper calls and constrain scalar values before pointer arithmetic.
  • The perf-event record size is clamped with verifier-visible operations before submission.
  • The shared syscall-exit helper restricts the return-value argument index to less than 16 because the Rocky Linux 8.10 verifier did not accept the broader bound used by the generic interface.
  • Memory-related syscall events use dedicated typed tracepoints on the target kernel instead of relying only on a more complex generic dispatcher.
  • Path reconstruction is limited to 20 components, VMA tree search to 35 levels, string arrays to 38 elements, event arguments to 32 entries, and temporary paired-probe arguments to seven values.

The Makefile compiles the object with optimisation and debugging metadata for the BPF target and defines the x86 architecture macros. These settings agree with the compatibility branches and manual register fallback. They should be reported as concrete build assumptions rather than as architecture-independent portability.

  • Filesystem activity: security_file_open, open, chmod, chown, security_file_ioctl, security_file_permission, kernel file-read hooks, mount and unmount hooks, unlink, rename, symlink, node creation, and memfd_create.
  • Memory and namespaces: mmap, mprotect, pkey_mprotect, process-to-process memory reads and writes, LSM memory hooks, setns, unshare, namespace switching, and cgroup task or directory operations.
  • Kernel integrity and eBPF activity: BPF command, map and program mediation, module load and free, module initialisation, procfs creation, kprobe registration, and kernel-symbol lookup.
  • Socket and network activity: socket creation, bind, listen, connect, accept and option changes, plus cgroup ingress and egress selectors. The current local registry reclassifies receive/send and related socket programs as internal dependencies; this uncommitted distinction must be rechecked before finalising the appendix.

The appendix table should eventually contain the logical event name, physical attachment points, attachment type, entry/return model, principal fields, and target-kernel validation status. It should be generated from or mechanically checked against the authoritative probe and event registries to avoid future drift.

Editorial Corrections and Qualifications

  • A comment beside security_file_open still states that an entry/return open event could be added later. That event is already implemented. The comment is stale and must not guide the thesis description.
  • The existence of versioned policy and filter maps does not prove that every rich policy predicate is active in kernel space. The exact UID prefilter is directly present in the common initialisation path; broader policy behaviour belongs to the userspace/policy audit.
  • CO-RE must not be presented as supplying absent hooks, helpers, attachment mechanisms or verifier features. The source contains explicit target-specific fallbacks precisely because relocatable field access is insufficient on its own.
  • Entry-only security hooks report an observed request or mediation point. They must not be described as proof that the operation ultimately succeeded.
  • The active transport is perf-event based. Ring-buffer declarations are retained for flexibility but are not evidence of current ring-buffer operation.
  • Some source comments retain names inherited from the reference project. They are implementation provenance artefacts and should not appear as the name of the thesis prototype.
  • The current system monitors module and kernel-integrity activity but does not implement hidden-module detection or comprehensive kernel-tampering detection.

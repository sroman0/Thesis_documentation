Chapter 6 Cross-Pod Agent Workflow

Binding decision: Chapter 6 presents only the completed cross-Pod Minikube experiment. The older one-Pod, three-container experiment and its five-run benchmark are excluded.

Verified baseline

  • Functional campaign: 3 benign runs with 0 alerts; 3 exploit runs with flag recovery and one complete alert each.
  • Filtered monitor: 3 runs, 0.46% mean CPU of one core, SD 0.02, mean run P95 1.00%.
  • Unfiltered monitor: 3 runs, 5.73% mean CPU; filtered reduction 91.97%.
  • Filtered maxima: 92.17 MiB cgroup memory and 36.97 MiB RSS.
  • Six monitored runs: no reported loss diagnostic and no restart delta.
  • No-monitor duration is excluded from overhead conclusions.

Pipeline

  1. Wave 1: run Agents 1–4 in parallel.
  2. Gate A: read all four audits and resolve blockers.
  3. Wave 2: run Agent 5 and approve its binding synthesis.
  4. Wave 3: run Agent 6 to update only Chapter 6.
  5. Wave 4: run Agent 7 as an independent reviewer.

Chapter boundaries

Chapters 2–5 own theory, architecture, hooks and user-space implementation. Chapter 6 owns protocol, controls, observations, measurements and validity. Full commands and manifests remain in minikube-ctf-cross-pod-laboratory.html. Target 3,000–3,800 words, 12–15 pages, at most two figures and three tables, and no source listings.

The CPU result is monitor-container user-space cgroup consumption as a percentage of one core. It is not total eBPF, application or system overhead. ATT&CK remains classification metadata. Do not claim cross-node visibility, detection accuracy, loss-free transport, enforcement or production readiness.

Acceptance gates

  • A: four fresh audits grounded in raw cross-Pod evidence.
  • B: synthesis defines claims, labels, visuals and exclusions.
  • C: Chapter 6 builds and every number is traceable.
  • D: final review has no unresolved high-severity finding.

Superseded brief. This page describes the earlier shared-Pod experiment. Use the current cross-Pod evidence brief.

This is the shared evidence brief for Experimental Evaluation. It defines what is currently supported, what remains provisional, and how the chapter must differ from the design and implementation chapters.

Chapter Purpose

Chapter 6 evaluates the prototype through a controlled Minikube experiment. A vulnerable AES-beta CTF service, an attack trigger and the privileged eBPF monitor run as three containers in one Pod. The chapter must connect the controlled input to kernel evidence, detector output and measured resource consumption. It is an evaluation narrative, not a deployment tutorial or a repetition of detector implementation.

Current Supported Results

  • All three benign runs completed without an AES-beta alert.
  • All four observed malicious sequences produced one structurally valid collective alert and no diagnosed perf loss.
  • Three exploit clients received the synthetic flag; one client did not, although the monitored shell, cat and successful file open still occurred.
  • The Pod remained 3/3 Running without restarts.
  • The replicated filtered profile measured 0.39% mean user-space monitor CPU with 0.02 sample standard deviation; all five run means were below 5%.
  • The replicated unfiltered profile measured 4.87% mean monitor CPU and a mean per-run P95 of 7.72%.
  • Filtering reduced mean monitor-container CPU by 91.99%; all ten monitored runs produced one alert and no loss diagnostic.
Performance claim boundary. The user-space monitor CPU gate is achieved for the filtered profile. Do not restate this as total system overhead: eBPF work in observed task context is not fully attributed to the monitor cgroup, and node CPU remained close to saturation in all profiles.

Terminology and Claims

  • Use British English and never use the internal tool name.
  • Prefer point detector and collective detector in evaluation prose; the experiment directly evaluates one collective detector.
  • Say cross-container visibility on one shared node kernel, not cluster-wide monitoring.
  • Distinguish exploit success at the client from detection of host behaviour.
  • Distinguish a diagnosed absence of perf loss from proof that no record was ever lost.
  • Describe the monitor as observational, not enforcing or production-ready.

Preferred Visuals

  • One three-container Pod diagram that answers where the attack and monitoring components run.
  • One attack-to-evidence sequence that answers which four observations complete the detector.
  • One functional-results table for benign and exploit repetitions.
  • At most two performance plots after replicated data exist: CPU by profile and memory or workload duration by profile.
Writing principle. Every result paragraph should identify the input, the measured or observed output, the comparison being made and the limitation of that comparison. Raw logs support the prose; they should not dominate it.

Purpose

Chapter 5 explains the implementation that begins after the kernel submits a record through the perf buffer. Its subject is the Go control and data path: runtime bootstrap, probe planning, event decoding and admission, policy and detector execution, alert presentation, operational logging and packaging. The chapter must describe implementation mechanisms without repeating the architecture already established in Chapter 3.

  1. Loader, Probe Registry and Attachment Lifecycle
  2. User-Space Decoder and Event Registry

  5. Output and Structured Logging

This is a starting hypothesis, not a frozen table of contents. The editorial synthesis may merge event selection into runtime planning or split the policy/detector section if doing so gives each mechanism one clear owner and removes repeated pipeline descriptions.

Implementation Questions

Bootstrap

How do configuration, policy scope and detector requirements become one selected event set and one owned attachment plan?

Event contract

Where does binary decoding end, what exactly is normalisation, and which registry is authoritative for event names and schemas?

Admission

Which filters run before loading, after decoding and before detector dispatch, and what does each rejection prevent?

Detection

Which work is compiled at bootstrap, which work remains on the hot path, and how are point and collective alerts produced?

Bounded state

How are process, parent, resource, cgroup and composite keys constructed, expired, evicted and deduplicated?

Operational boundary

How are event and alert data kept separate from Zap and libbpf diagnostics, and what is actually packaged in the image?

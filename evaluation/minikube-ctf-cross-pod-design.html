Cross-Pod Minikube Experiment Design

SELF-CONTAINED DESIGN — FUNCTIONAL EVIDENCE COMPLETE

This document preserves the Phase 2 design and records the current status of its acceptance criteria. Deployment, isolation, Service communication and controlled telemetry have been verified. Three benign and three exploit runs have also been executed and independently audited. A replicated performance study was subsequently executed on the same cross-Pod node.

Research Question

Can the eBPF monitor, running in its own Kubernetes Pod, observe and detect the AES-beta exploitation sequence generated in an independent target Pod when the attack client executes from a third Pod on the same Minikube node?

A second evaluation question asks whether the monitor's mean user-space CPU remains at or below 5% of one core during the exploit workload in its canonical filtered configuration.

Volumes and Mounts

  • The monitor alone mounts /sys/kernel/btf read-only, /sys/fs/bpf and /sys/kernel/tracing from the node.
  • The monitor reads the policy catalogue from its image, receives the detector ConfigMap read-only and uses a bounded writable emptyDir at /tmp.
  • The target alone receives the flag Secret.
  • The trigger receives only a bounded writable emptyDir at /tmp.
  • No Docker socket, host root filesystem or shared application volume is planned.

Network Configuration

  • The target continues to bind 0.0.0.0:1337; no source change is required.
  • The trigger receives TARGET_HOST=aes-beta-target-cross-pod and TARGET_PORT=1337.
  • The Service selects only the target Deployment label.
  • No host port, NodePort, Ingress or hostNetwork is introduced.
  • A NetworkPolicy is not part of the initial experiment because it would add another variable and its enforcement depends on the active CNI.

Monitor and Detector Configuration

The canonical evaluation profile preserves the existing monitor arguments: policy path, one detector path, --alerts-only, JSON alerts, exact kernel UID filter 10001, JSON diagnostics and info logging. This keeps the Pod topology and network path as the main changed variables.

Phase 5 requires raw-event visibility. The planned procedure temporarily removes only --alerts-only from the DaemonSet arguments, records the rollout and controlled test, then reapplies the canonical manifest and verifies a fresh stable rollout before benign evaluation. This temporary mode must not be used for Phase 6 or Phase 7 results.

Observed Runtime Outcomes

  • The experiment uses the dedicated cross-pod Minikube profile.
  • The three required images are loaded into the cross-pod profile.
  • Actual Minikube, Kubernetes, Docker and kernel versions are recorded in the deployment document.
  • The active CNI resolves and routes the ClusterIP Service as planned.
  • All three pod cgroups were read without adding tooling.
  • The benign control completed without an AES-beta alert, and the unchanged detector completed its four-step sequence in all three exploit runs.

Phase 2 Decision

Phase 2 concluded that the topology required configuration and orchestration changes only. Later phases confirmed this: application, eBPF, Go runtime and detector code remained unchanged. One scenario-runner configuration defect in client-side flag validation was corrected and preserved in the evidence.

Cross-Pod AES-beta Experiment

A direct account of how the cross-Pod laboratory is created and tested. Every command is executed manually and followed by its purpose, relevant options and expected evidence.

Concepts Prepare Deploy Validate Test Results

1. Minikube, Kubernetes and the Topology

Kubernetes runs containerised workloads as Pods. A Deployment maintains the target replica, a Service gives that target a stable network endpoint, and a DaemonSet places one monitor on each selected node. Minikube creates a local Kubernetes cluster; this experiment uses one Docker-backed node so all three Pods share one Linux kernel.

This shared kernel is the central assumption of the experiment. The monitor does not enter the target Pod and does not receive its process namespace. Instead, its eBPF programs attach to the node kernel and observe events produced by workloads scheduled on that node.

trigger Pod → ClusterIP Service:1337 → target Pod → node kernel hooks → monitor Pod
ResourcePurposeSecurity identity
Monitor DaemonSetLoads eBPF programs and evaluates the AES-beta detector.Privileged UID 0; hostPID: false.
Target DeploymentRuns the vulnerable AES-beta service.Non-root UID/GID 10001.
Trigger PodRuns the benign client or exploit.Non-root UID/GID 10002.
ClusterIP ServiceRoutes TCP/1337 from trigger to target.Cluster-internal endpoint.
Two meanings of “flag”. A command-line flag is an option such as --context or --timeout. The CTF flag is the synthetic value openECSC{ebpf_cross_pod_evaluation}, mounted only in the target. Recovering it proves that the exploit reached and read the protected test file; it is not a real competition secret.

2. Prepare the Cluster and Images

Work from the project root and record the environment.

cd /home/simone/project/demo_project
date -u
cat /etc/os-release
uname -r
docker --version
minikube version
kubectl version --client

Meaning. cd fixes the working directory so every relative path below is unambiguous. date -u records a UTC reference for later log correlation. /etc/os-release and uname -r identify the host distribution and kernel. The three version commands record the Docker, Minikube and Kubernetes client versions; --client avoids requiring a running cluster at this point.

Create the single-node Minikube profile.

minikube start -p cross-pod --driver=docker \
  --kubernetes-version=v1.30.0 --cpus=2 --memory=4096

kubectl --context cross-pod get nodes -o wide

Purpose. The first command creates the reproducible single-node cluster. The second confirms that its Kubernetes node is Ready and displays placement information.

  • -p cross-pod names the Minikube profile, keeping its state separate from other clusters.
  • --driver=docker runs the Minikube node as a Docker container.
  • --kubernetes-version=v1.30.0 fixes the Kubernetes server version used in the experiment.
  • --cpus=2 and --memory=4096 allocate two virtual CPUs and 4096 MiB to the node.
  • --context cross-pod directs kubectl to this cluster; -o wide adds node address and runtime columns.

Stage and verify the approved openECSC challenge artefacts.

CHALLENGE=../openECSC-2024/teamitaly-preselection-ctf/pwn01
STAGE=k8s/minikube-ctf/.build/upstream
mkdir -p "$STAGE"

sha256sum \
  "$CHALLENGE/src/build/aes-beta" \
  "$CHALLENGE/src/glibc/ld-linux-x86-64.so.2" \
  "$CHALLENGE/src/glibc/libc.so.6"

install -m 0644 "$CHALLENGE/src/build/aes-beta" "$STAGE/aes-beta"
install -m 0644 "$CHALLENGE/src/glibc/ld-linux-x86-64.so.2" \
  "$STAGE/ld-linux-x86-64.so.2"
install -m 0644 "$CHALLENGE/src/glibc/libc.so.6" "$STAGE/libc.so.6"

Purpose. The target and exploit must use the exact challenge binary, loader and C library for which the exploit was prepared.

CHALLENGE and STAGE are shell variables for the source and Docker build context. mkdir -p creates the staging directory and does not fail if it already exists. sha256sum calculates each artefact digest, which must match the table below. install -m 0644 copies the verified file with read permissions for all users and write permission only for its owner.

Build and load the three images.

docker build --network=host -t demo-project-ebpf:latest .

docker build -f k8s/minikube-ctf/images/target/Dockerfile \
  -t aes-beta-target:local k8s/minikube-ctf

docker build -f k8s/minikube-ctf/images/trigger/Dockerfile \
  -t aes-beta-trigger:local k8s/minikube-ctf

minikube image load -p cross-pod demo-project-ebpf:latest
minikube image load -p cross-pod aes-beta-target:local
minikube image load -p cross-pod aes-beta-trigger:local
minikube image ls -p cross-pod

Purpose. Three independent images are required: the monitoring tool, the vulnerable service and the two clients.

  • docker build creates an image from a Dockerfile and build context. --network=host gives the monitor build access to the host network for dependency retrieval. -f selects the target or trigger Dockerfile, and -t assigns the image name expected by the manifests.
  • minikube image load copies each local image into profile cross-pod. This is required because the manifests use imagePullPolicy: Never and therefore do not contact an external registry.
  • minikube image ls verifies that all three names are available inside the node.
Rebuilding an existing latest tag. If the DaemonSet keeps starting an older image, verify the image ID on the host and node. A crashing container can keep the old node image referenced. Remove only that stale node tag, reload it, and restart the DaemonSet: 
docker image inspect demo-project-ebpf:latest --format '{{.Id}} {{.Created}}'
minikube -p cross-pod ssh "docker image inspect demo-project-ebpf:latest --format '{{.Id}} {{.Created}}'"
minikube -p cross-pod ssh "docker image rm --force demo-project-ebpf:latest"
minikube image load -p cross-pod demo-project-ebpf:latest
kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout restart daemonset/project-monitor-cross-pod
kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout status daemonset/project-monitor-cross-pod --timeout=180s
The two inspection commands must report the same image ID before the rollout is accepted.

3. Configure and Deploy Kubernetes

Validate the manifests and create the namespace.

kubectl --context cross-pod apply --dry-run=client --validate=true \
  -f k8s/minikube-ctf-cross-pod/manifests/

kubectl --context cross-pod apply \
  -f k8s/minikube-ctf-cross-pod/manifests/namespace.yaml

Purpose. The dry run checks local YAML structure before changing the cluster. The second command then creates the dedicated namespace that isolates names and experiment resources.

  • apply creates a missing resource or updates an existing one to match the manifest.
  • --dry-run=client performs local processing without contacting the API server for creation.
  • --validate=true checks fields against the schema known to kubectl.
  • -f supplies a manifest file or directory.

Create the detector ConfigMap and target-only synthetic flag Secret.

kubectl --context cross-pod -n ebpf-ctf-cross-pod create configmap \
  project-monitor-cross-pod-detector \
  --from-file=aes-beta-command-execution.yaml=k8s/minikube-ctf/detectors/aes-beta-command-execution.yaml \
  --dry-run=client -o yaml | kubectl --context cross-pod apply -f -

kubectl --context cross-pod -n ebpf-ctf-cross-pod create secret generic \
  aes-beta-cross-pod-flag \
  --from-literal='flag=openECSC{ebpf_cross_pod_evaluation}' \
  --dry-run=client -o yaml | kubectl --context cross-pod apply -f -

Purpose. The ConfigMap makes the committed detector definition available to the monitor. The Secret stores the synthetic CTF flag and is mounted only at /opt/aes-beta/flag in the target.

  • -n ebpf-ctf-cross-pod selects the experiment namespace.
  • --from-file=key=path stores the detector file under the specified ConfigMap key.
  • --from-literal=flag=... creates the Secret entry named flag. Quoting prevents the shell from interpreting braces.
  • --dry-run=client -o yaml renders the resource instead of creating it immediately. The pipe passes that YAML to kubectl apply -f -, where the final hyphen means “read from standard input”.

The Secret protects the value from being committed in a manifest, but Kubernetes Secrets are not encrypted merely because they are Secrets; this laboratory uses only a synthetic value.

Apply the workloads, Service and monitor.

kubectl --context cross-pod apply \
  -f k8s/minikube-ctf-cross-pod/manifests/target-deployment.yaml \
  -f k8s/minikube-ctf-cross-pod/manifests/target-service.yaml \
  -f k8s/minikube-ctf-cross-pod/manifests/trigger-pod.yaml \
  -f k8s/minikube-ctf-cross-pod/manifests/monitor-daemonset.yaml

kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout status \
  deployment/aes-beta-target-cross-pod --timeout=180s
kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout status \
  daemonset/project-monitor-cross-pod --timeout=180s
kubectl --context cross-pod -n ebpf-ctf-cross-pod wait \
  --for=condition=Ready pod/aes-beta-trigger-cross-pod --timeout=180s

Purpose. The multi-file apply creates the target Deployment, Service, trigger Pod and monitor DaemonSet. The canonical policy catalogue is already present in the monitor image. The following commands block until the components are usable.

  • rollout status deployment/... waits for the target replica to become available.
  • rollout status daemonset/... waits for the node monitor to become available.
  • wait --for=condition=Ready waits for the standalone trigger Pod.
  • --timeout=180s turns a stalled deployment into an explicit failure after three minutes.

The DaemonSet starts the monitoring executable with the following options. They are part of the deployed container command even though they are supplied through YAML rather than typed separately in the terminal.

Monitor optionMeaning in this experiment
--policy /etc/project/policies/aes-beta-process-observation.yamlLoads the canonical image policy that restricts collection to sched_process_exec, security_file_open and open.
--detectors /etc/project/detectors/aes-beta-command-execution.yamlLoads the collective detector that recognises the shell, cat and flag-access sequence.
--alerts-onlySuppresses ordinary event output while preserving detector evaluation and alerts.
--alerts-output jsonProduces structured alerts that retain the four evidence events.
--kernel-filter-uid-enabled --kernel-filter-uid 10001Rejects events whose effective UID is not the target UID before transport to user space.
--log-format json --log-level infoWrites structured operational diagnostics at informational severity or above.

The target listens on 0.0.0.0:1337, making the service reachable outside its Pod. The trigger receives TARGET_HOST=aes-beta-target-cross-pod and TARGET_PORT=1337, so its clients resolve the Kubernetes Service instead of connecting to loopback.

4. Validate Placement, Isolation and Visibility

Verify independent Pod identities, same-node placement and Service routing.

kubectl --context cross-pod -n ebpf-ctf-cross-pod get pods \
  -o custom-columns='NAME:.metadata.name,POD_UID:.metadata.uid,POD_IP:.status.podIP,NODE:.spec.nodeName,RESTARTS:.status.containerStatuses[0].restartCount,HOST_PID:.spec.hostPID'

kubectl --context cross-pod -n ebpf-ctf-cross-pod get service,endpointslice -o wide

TARGET=$(kubectl --context cross-pod -n ebpf-ctf-cross-pod get pod \
  -l app.kubernetes.io/component=target -o jsonpath='{.items[0].metadata.name}')
MONITOR=$(kubectl --context cross-pod -n ebpf-ctf-cross-pod get pod \
  -l app.kubernetes.io/component=monitor -o jsonpath='{.items[0].metadata.name}')

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec "$TARGET" -- cat /proc/1/cgroup
kubectl --context cross-pod -n ebpf-ctf-cross-pod exec aes-beta-trigger-cross-pod -- cat /proc/1/cgroup
kubectl --context cross-pod -n ebpf-ctf-cross-pod exec "$MONITOR" -- cat /proc/1/cgroup

Purpose. These commands establish that the topology actually differs at Pod level while remaining node-local.

  • get pods -o custom-columns=... extracts Pod name, Kubernetes UID, IP, node, restart count and hostPID directly from the API.
  • get service,endpointslice -o wide connects the stable Service identity to the selected target Pod endpoint on TCP/1337.
  • -l app.kubernetes.io/component=... selects a Pod by label instead of using a generated name. -o jsonpath=... extracts that name into a shell variable.
  • kubectl exec POD -- COMMAND runs a command inside a selected container; -- separates kubectl options from the in-container command. Reading /proc/1/cgroup exposes the local cgroup path.

Expected evidence is three different Pod UIDs, IPs, container identities and cgroups, with one common node. The EndpointSlice must reference the target Pod on port 1337.

Perform the one-time raw-event visibility check.

kubectl --context cross-pod -n ebpf-ctf-cross-pod patch daemonset \
  project-monitor-cross-pod --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/args/4"}]'

kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout status \
  daemonset/project-monitor-cross-pod --timeout=180s
TARGET=$(kubectl --context cross-pod -n ebpf-ctf-cross-pod get pod \
  -l app.kubernetes.io/component=target -o jsonpath='{.items[0].metadata.name}')
MONITOR=$(kubectl --context cross-pod -n ebpf-ctf-cross-pod get pod \
  -l app.kubernetes.io/component=monitor -o jsonpath='{.items[0].metadata.name}')
START=$(date -u +%Y-%m-%dT%H:%M:%SZ)

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec "$TARGET" -- \
  /bin/cat /proc/self/status
kubectl --context cross-pod -n ebpf-ctf-cross-pod logs "$MONITOR" \
  --since-time="$START" --timestamps=true

kubectl --context cross-pod apply \
  -f k8s/minikube-ctf-cross-pod/manifests/monitor-daemonset.yaml
kubectl --context cross-pod -n ebpf-ctf-cross-pod rollout status \
  daemonset/project-monitor-cross-pod --timeout=180s

Purpose. The canonical monitor prints alerts only. This temporary change exposes raw events to prove that a monitor in another Pod can see target activity.

  • patch daemonset --type=json applies an RFC 6902 JSON Patch. -p contains one removal operation for argument index 4, currently --alerts-only.
  • START=$(date -u ...) records the UTC boundary immediately before the controlled target command.
  • /bin/cat /proc/self/status creates known process-execution and file-access activity under target UID 10001.
  • logs --since-time="$START" excludes older records; --timestamps=true preserves their Kubernetes log timestamps.
  • Reapplying the committed DaemonSet manifest restores --alerts-only and the canonical test configuration.

The JSON patch depends on the current argument ordering and is appropriate only for this recorded manifest.

5. Run the Functional Tests Manually

Terminal 1: retain monitor output while the scenarios run.

mkdir -p /tmp/cross-pod-manual-evidence
kubectl --context cross-pod -n ebpf-ctf-cross-pod logs \
  -f daemonset/project-monitor-cross-pod --timestamps=true \
  | tee /tmp/cross-pod-manual-evidence/monitor.log

Purpose. This terminal observes the monitor continuously while the second terminal runs workloads. mkdir -p creates the evidence directory. logs -f follows new output, --timestamps=true prefixes Kubernetes timestamps, and tee both displays and stores the stream.

Terminal 2: execute three benign controls.

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=benign-cross-pod-01 \
  /opt/trigger/run-benign

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=benign-cross-pod-02 \
  /opt/trigger/run-benign

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=benign-cross-pod-03 \
  /opt/trigger/run-benign

Purpose. The benign client exercises the same Service and vulnerable application without requesting the flag. Three distinct executions check that ordinary challenge use does not complete the attack sequence.

exec starts the client inside the independent trigger Pod. env RUN_ID=... assigns a unique identifier to its JSON output, and /opt/trigger/run-benign sends the known plaintext and verifies the returned XOR ciphertext. Each run should report result: pass; the monitor should emit no AES-beta alert.

Execute three exploit runs with the corrected flag pattern.

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=exploit-cross-pod-01 \
  'FLAG_PATTERN=^openECSC\{[A-Za-z0-9_-]+\}$' /opt/trigger/run-exploit

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=exploit-cross-pod-02 \
  'FLAG_PATTERN=^openECSC\{[A-Za-z0-9_-]+\}$' /opt/trigger/run-exploit

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-trigger-cross-pod -- env RUN_ID=exploit-cross-pod-03 \
  'FLAG_PATTERN=^openECSC\{[A-Za-z0-9_-]+\}$' /opt/trigger/run-exploit

Purpose. These commands repeat the controlled exploit three times without moving the client into the target Pod.

  • RUN_ID distinguishes each application result.
  • FLAG_PATTERN is a regular expression used only by the client to validate the recovered value. ^ and $ anchor the complete string, escaped braces match the literal CTF format, and the character class accepts the controlled payload text.
  • /opt/trigger/run-exploit leaks the library base, reconstructs the canary with 1,792 candidate workers and creates one final payload worker.

Each run should recover the synthetic flag, report 1,793 workers and produce one alert containing four ordered events: /bin/sh execution, /bin/cat execution, resolved flag access and successful open. Flag recovery and detector success are checked independently.

Inspect alerts, diagnostics and Pod stability.

grep '"detector_id":"aes-beta-command-execution"' \
  /tmp/cross-pod-manual-evidence/monitor.log

grep -Ei 'lost|perf.*loss' /tmp/cross-pod-manual-evidence/monitor.log

kubectl --context cross-pod -n ebpf-ctf-cross-pod get pods \
  -o custom-columns='NAME:.metadata.name,READY:.status.containerStatuses[0].ready,RESTARTS:.status.containerStatuses[0].restartCount'

Purpose. The first grep extracts detector alerts by stable detector ID. The second searches diagnostics for loss-related terms: -E enables the alternative expression, and -i ignores case. The final kubectl get checks readiness and restart counts after the workloads.

An empty loss search means no matching diagnostic was printed; it is not an independent proof of zero transport loss.

Historical test-harness anomaly. The first two recorded exploit clients recovered the flag and produced complete alerts but returned failure because the reused client expected THESIS{...}; the first correction was malformed. The commands above contain the verified literal openECSC{...} pattern.

6. Observed Result and Boundary

Supported conclusion. On the evaluated single-node Minikube cluster, the monitoring Pod observed and detected the exploit executed in an independent target Pod. This does not demonstrate cross-node collection, least-privilege deployment, enforcement or general detector coverage.

7. Cleanup

kubectl --context cross-pod delete namespace ebpf-ctf-cross-pod
minikube stop -p cross-pod

# Remove the complete local cluster only when it is no longer needed:
minikube delete -p cross-pod

Meaning. Deleting the namespace removes only the experiment resources. minikube stop -p cross-pod stops the node but preserves its profile and images for later reuse. minikube delete -p cross-pod permanently removes that local cluster and should be used only after evidence has been collected.

Raw evidence from the recorded experiment is preserved under demo_project/k8s/minikube-ctf-cross-pod/evidence/cross-pod-20260817T052019Z/.

The functional procedure and the separate cross-Pod performance evaluation are complete. The reported CPU and memory values come from this topology; measurements from the earlier shared-Pod laboratory are not substituted.

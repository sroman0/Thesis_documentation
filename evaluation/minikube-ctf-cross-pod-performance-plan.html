Cross-Pod Minikube Performance Evaluation Plan

STATUS: EXECUTED — PRIMARY GATES PASS

Official dataset: cross-pod-performance-20260819T070557Z. The protocol was executed on the same cross-pod Minikube node used for functional evaluation. See the compact results report.

Question and Acceptance Criterion

The primary question is whether the monitor's mean user-space CPU remains at or below 5% of one CPU core while the AES-beta exploit runs in the canonical cross-Pod configuration. The study also measures memory, target cost, node utilisation, workload duration, alerts, perf-event loss diagnostics and Pod restarts.

The 5% gate applies only to the monitor container's user-space cgroup CPU. eBPF programs execute in the context of observed kernel activity, so this value must not be described as total system overhead. Node CPU provides system-level context; no-monitor duration is retained as descriptive evidence subject to the post-run limitation below.

Fixed Environment

  • Minikube profile cross-pod, one node, two CPUs and 4096 MiB.
  • Monitor DaemonSet, target Deployment and trigger Pod on that node.
  • Target UID 10001, trigger UID 10002 and Service-based TCP/1337 communication.
  • The same image IDs, policy, detector, event scope and synthetic flag for every measured run.
  • No additional intentional workload on the host or Minikube node during the benchmark.

Each profile requires three independent runs, for nine official runs in total. Use three rotated rounds: filtered → unfiltered → no-monitor, then unfiltered → no-monitor → filtered, and finally no-monitor → filtered → unfiltered. Recreate the monitor Pod after each profile change and record its new container ID and cgroup.

Measurement Window

Use a one-second sampling interval. Start the sampler, allow a ten-second warm-up, execute one exploit run and continue sampling until a fixed 75-second window ends. Summaries must use the explicitly recorded workload interval for workload comparisons; retain the complete sampling window for audit and idle-context inspection.

The exploit client must still report 1,793 workers and recover the synthetic flag. Filtered and unfiltered runs must each produce one complete AES-beta alert. Any failed workload, missing alert, loss diagnostic or restart remains in the dataset and must not be silently replaced.

Measurement Source

The recorded cross-Pod environment uses cgroup v1. Resolve the current container IDs through Kubernetes, then locate their cgroup files on the Minikube node. Calculate one-core CPU percentage from successive cpuacct.usage values:

CPU percentage = (delta container CPU nanoseconds / delta wall nanoseconds) * 100

Read memory.usage_in_bytes, total_rss from memory.stat, and pids.current for the monitor and target. Read /proc/stat in the Minikube node for total node CPU. The sampler must run outside the measured container so that its own work is not charged to the monitor.

Implemented Measurement Pipeline

  1. deploy-performance-profile.sh applies filtered, unfiltered and no-monitor states and restores the canonical filtered DaemonSet.
  2. sample-cross-pod-performance.sh discovers monitor and target container IDs in separate Pods and samples their cgroup v1 counters on the cross-pod node.
  3. run-performance-case.sh records workload boundaries and preserves application, detector, loss and restart evidence without retry.
  4. run-performance-calibration.sh executes one explicitly excluded calibration run.
  5. run-replicated-performance.sh requires the explicit CALIBRATION_APPROVED=1 acknowledgement and implements the three rotated rounds; summarize-performance.sh derives aggregate values only from preserved TSV evidence.

Static status: PASS WITH ONE TOOL UNAVAILABLE. All scripts pass bash -n; the unfiltered manifest transformation preserves the canonical configuration while removing only the UID filter; the alert-evidence predicate matches a preserved four-event alert; and the offline summariser passes a synthetic nine-run test. shellcheck is not installed on the host and was therefore not executed.

First runtime attempt: REJECTED. The first calibration, preserved under performance-calibration-20260819T065500Z, completed the exploit in 45,652 ms, recovered the flag with 1,793 workers, produced one complete alert, and showed no loss diagnostic or restart. Its CPU columns were empty because unparenthesised AWK ternaries after printf were parsed as output redirections. The summary incorrectly converted those missing values to zero. This attempt is invalid for performance interpretation.

The CPU calculations now use explicit conditional branches, and both the sampler and run coordinator reject missing or non-numeric CPU fields. The corrected formula returns 50.00 for a controlled 1/2 ratio on both host and Minikube node, while the malformed first-calibration TSV is rejected. A fresh calibration in a new evidence directory must pass before the nine official runs are authorised.

A three-second smoke test on the active cluster then produced numeric samples for all three CPU fields: monitor 0.02--0.03% of one core, idle target 0.00%, and node 7.00--9.55%. These values validate the corrected sampling path only and are not part of the performance results.

Corrected calibration: PASS. The run under performance-calibration-20260819T070018Z produced 72 structurally valid samples, including 45 in the exploit interval. The exploit completed in 47,101 ms with 1,793 workers and flag recovery. One complete alert was recorded, with no loss diagnostic or restart. Monitor CPU was 0.50% mean, 1.03% P95 and 1.39% peak of one core; peak monitor cgroup memory was 93.07 MiB and RSS was 37.33 MiB. The node averaged 92.25% of its two-CPU capacity during the brute-force workload. These calibration values validate the method but remain excluded from the official result set.

Execution Result

The nine official runs completed without retry. All nine exploit workloads recovered the flag with 1,793 workers. The six monitored runs generated one complete alert each, with no reported perf-event loss or Pod restart.

Filtered monitor CPU averaged 0.46% of one core (SD 0.02; run range 0.44--0.47%), compared with 5.73% unfiltered. The measured reduction was 91.97%. Maximum filtered cgroup memory was 92.17 MiB and maximum RSS was 36.97 MiB.

The node remained near saturation during all profiles. The saved no-monitor snapshots also showed the former monitor Pod as Terminating immediately after DaemonSet deletion. These controls remain preserved, but their durations are not used to claim causal overhead. The profile script now waits for and verifies full Pod deletion before future controls.

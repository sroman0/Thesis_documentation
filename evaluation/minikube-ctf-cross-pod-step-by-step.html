Step 1 — Requirements Inspection

Purpose. Verify the components required by the cross-Pod laboratory without changing runtime or repository state.

Observed result. The target can bind 0.0.0.0:1337; trigger clients accept TARGET_HOST and TARGET_PORT. The monitor supports exact effective-UID filtering for UID 10001 and the required four-step AES-beta collective detector is available.

Purpose. Separate monitor, target and trigger while preserving the single Minikube node, images, detector semantics and process identities.

Observed result. A DaemonSet monitor, one-replica target Deployment, ClusterIP Service and long-running trigger Pod were selected. Runtime properties remain NOT YET TESTED.

Step 5 — Isolation, Networking and eBPF Visibility

Purpose. Test the assumptions required by the later scenarios without executing either the benign client or the exploit.

Independent Pod Evidence

Expected result. Three distinct Pod UIDs, IPs, container identities and pod cgroups on the same node, with hostPID: false.

Observed result. Target, trigger and monitor had different Pod UIDs, IP addresses and Docker container IDs. Their /proc/1/cgroup paths contained different Kubernetes Pod UIDs, and all three cgroup evidence files had different hashes. The effective specification reported hostPID=false for every Pod.

Interpretation. PASS. The workloads are separate Pods and containers while sharing the node kernel required for node-local eBPF observation.

Service Communication

Command. A Python standard-library client in the trigger resolved the configured TARGET_HOST and opened one TCP connection. It did not invoke the benign or exploit runner.

python3 -c '... socket.create_connection((TARGET_HOST, TARGET_PORT), 3) ...'

Observed result. aes-beta-target-cross-pod resolved to ClusterIP 10.102.19.49. The socket peer was 10.102.19.49:1337, the EndpointSlice referenced 10.244.0.3:1337, and the target logged a session from trigger IP 10.244.0.4.

Interpretation. PASS. Communication used the Kubernetes Service and independent Pod network, not 127.0.0.1.

Controlled Target Telemetry

The DaemonSet was temporarily patched to remove only --alerts-only. The exact UID filter, policy and detector remained unchanged. The first orchestration command returned status 1 after rollout because newline-free jsonpath output caused Bash read to return EOF. Runtime inspection showed that the Pod itself was Ready, had zero restarts and correctly reported alerts_only=false. The two affected repository scripts were corrected to use direct Bash file expansion and passed bash -n.

Controlled command.

kubectl --context cross-pod -n ebpf-ctf-cross-pod exec \
  aes-beta-target-cross-pod-86846476fc-2zqhb -- \
  /bin/cat /proc/self/status

Observed result. The command reported real/effective UID 10001. The independent monitor recorded eight UID-10001 records, including one sched_process_exec for /bin/cat, resolved security_file_open evidence and a successful open for /proc/self/status.

Interpretation. PASS. A monitor in its own Pod observed controlled process and file activity generated in the target Pod while hostPID remained false.

UID Filter Sanity Check

The same command was executed in the trigger Pod and its own /proc/self/status confirmed UID 10002. The monitor interval starting immediately before this command contained zero lines and zero UID-10002 records.

Interpretation. The controlled positive and negative cases are consistent with exact kernel admission for UID 10001. This does not prove isolation from every unrelated node process that might also use UID 10001.

Two initial grep counts used incorrect quoting or assumed direct JSON keys instead of the actual name/value argument representation. Both failed attempts remain in commands.log; corrected counts were then recorded from the unchanged raw logs.

Canonical Restoration

The committed DaemonSet manifest was reapplied after telemetry collection. The replacement monitor project-monitor-cross-pod-wx5zq reported alerts_only=true, exact UID filter 10001, one policy and one detector. All three Pods were Ready with zero restarts, no Warning events were present, and the loss-diagnostic scan returned no match.

Step 10 — Replicated Performance Evaluation

Purpose. Measure monitor CPU and memory, node utilisation, exploit duration, detection integrity and runtime stability on this same cross-Pod node.

Status. EXECUTED. The approved method used filtered, unfiltered and no-monitor profiles with three runs each, for nine official runs. No value from another topology was imported.

Implementation. Profile selection, cross-Pod cgroup sampling, single-run coordination, calibration, rotated execution and offline aggregation scripts are present. Bash syntax, profile rendering, alert-evidence validation and synthetic aggregation passed; shellcheck was unavailable. Runtime calibration remains pending.

First calibration attempt. The filtered workload completed successfully in 45,652 ms with 1,793 workers, flag recovery, one complete alert, no loss diagnostic and no restart. The CPU columns were empty, so the apparent 0.00 summary was rejected. The cause was an AWK parsing ambiguity in three CPU calculations. Explicit branches and structural TSV validation were added; the malformed evidence is preserved under performance-calibration-20260819T065500Z. A replacement calibration was then required.

Post-fix smoke test. A three-second read-only sample produced numeric monitor, target and node CPU fields. It did not execute an exploit and is not included in the evaluation dataset.

Corrected calibration. The second attempt produced 72 valid rows with no blank CPU fields and 45 samples inside the workload interval. The exploit passed in 47,101 ms, used 1,793 workers, recovered the flag and generated one complete alert. Monitor CPU was 0.50% mean, 1.03% P95 and 1.39% peak; losses and restarts were zero. The calibration is approved but excluded from the official dataset.

Official execution. The nine runs completed without retry. Filtered monitor CPU averaged 0.46% of one core (SD 0.02; range 0.44--0.47%), against 5.73% unfiltered, a measured reduction of 91.97%. Every monitored run recovered the flag and produced one complete alert; losses and restarts were zero.

Post-run audit. The snapshots taken immediately after each no-monitor profile change still showed the old monitor Pod as Terminating. A ten-second sampler warm-up preceded each exploit, but final Pod deletion was not independently timestamped. The no-monitor controls are retained and their durations are not used for a causal overhead claim. The profile script was then changed to wait for and verify complete monitor-Pod deletion.

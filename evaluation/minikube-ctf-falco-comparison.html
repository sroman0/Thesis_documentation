Falco Comparison on the AES-beta Workload

Functional and performance comparison performed on 11 September 2026

RESULT: COMPLETE. All six official Falco runs completed the exploit, recovered the synthetic flag and exposed the required shell, cat and file-open evidence. No Pod restarted and no matching event-loss warning appeared in the retained intervals.

Purpose

This test adds an external reference point to the prototype evaluation. Falco was selected because it is an established runtime security tool with eBPF collection, a rule engine and container enrichment. The comparison reuses the same AES-beta target, trigger Pod, Minikube node and cgroup-v1 sampling method used for the prototype.

The comparison addresses two questions. The functional check asks whether Falco can expose the host observations associated with the successful exploit. The performance check measures CPU and memory charged to the Falco container during the same 1,793-worker workload.

Preparation

The Falco image was pulled inside the Minikube node and its digest was recorded. A 30-second compatibility test confirmed that the modern eBPF engine could load on the target kernel. A separate smoke rule then observed a successful /bin/cat /etc/hostname execution under UID 10001 and attributed it to the AES-beta target Pod.

Three rules were created for the experiment:

  • successful execution of a shell;
  • successful execution of cat;
  • successful opening of /opt/aes-beta/flag.

Falco validated the rules before they were deployed. A functional exploit run then confirmed that all three observations were available. Falco produced separate rule alerts, while the prototype produced one collective alert containing four ordered records.

Important distinction. The two filtered profiles express a similar selection criterion, but they apply it at different stages. Falco evaluates the UID condition as part of its rule processing. The prototype can discard other UIDs in eBPF before their records are transferred to user space.

Execution Procedure

  1. The original monitor DaemonSet was removed so that it could not affect the Falco measurements.
  2. A Falco DaemonSet was created with one custom rules ConfigMap and the modern eBPF engine.
  3. Before each run, the requested rules profile was applied and the Falco Pod was restarted to create a fresh container cgroup.
  4. A ten-second warm-up preceded one execution of the AES-beta exploit.
  5. An external sampler read Falco, target and node counters once per second for 75 seconds.
  6. Only samples between the recorded exploit start and end times entered the run summary.
  7. Three runs per profile were executed in alternating order: F--U, U--F and F--U.

CPU is reported as a percentage of one core. Memory usage and total_rss come from the Falco container's cgroup-v1 counters. Every run also checked the exploit result, rule evidence, Pod restart delta and matching loss diagnostics.

Functional Observations

Every official run recovered openECSC{ebpf_cross_pod_evaluation}. Falco attributed the valid shell, cat and flag-open alerts to UID 10001, the AES-beta target container and its Kubernetes Pod. The successful open returned file descriptor 2.

Each run also contained a second shell alert with an unreadable command-line suffix. It followed the valid exploit activity but did not contribute additional evidence of success. The unfiltered runs contained one additional cat alert from UID 1000 on the host. This was the benchmark helper reading its saved trigger output. The filtered rules excluded that host activity.

These observations illustrate the output difference between the systems. Falco reported each matching operation separately and supplied container and Kubernetes enrichment. The prototype joined shell execution, cat execution, the resolved LSM file observation and the successful syscall result into one ordered alert.

The prototype's kernel-filtered mean was about one eleventh of the Falco filtered mean. Once the prototype's early UID filter was disabled, Falco used 0.84 percentage points less CPU on average. Falco also reached lower maximum cgroup memory values, while maximum RSS was close across the two systems.

The result supports the value of early admission in this controlled case. It does not establish a general ranking between the tools. Falco and the prototype use different collection paths, event models and alert semantics. Falco provides mature rule processing and Kubernetes enrichment; the prototype's experiment uses an LSM observation and explicit short-sequence correlation. The prototype and Falco campaigns were also performed on different dates, although they used the same node configuration, target images and workload design.

Validity Boundaries

  • Three runs per profile support a descriptive comparison only.
  • Mean node CPU remained between 93.30% and 97.45%, leaving little idle capacity.
  • The monitor metric covers CPU charged to the monitor container cgroup and excludes some kernel work caused by eBPF collection.
  • No matching loss warning was found; an independent event-completeness counter was not available.
  • The Falco UID condition and the prototype kernel UID filter operate at different stages.
  • The custom Falco rules reproduce the evidence needed by this scenario; they do not represent the complete Falco rules catalogue.
  • The experiment evaluates observation and alerting. Falco enforcement and the broader capabilities of either system were outside its scope.

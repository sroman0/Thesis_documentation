Cross-Pod Minikube Functional Evaluation

FUNCTIONAL EVALUATION COMPLETE AND AUDITED

Evaluation Boundary

This document records the functional runs executed after validating the three-Pod topology. Application success, detector output, transport-loss diagnostics and Pod stability are treated as separate observations. The monitor ran in canonical alerts-only mode with the exact kernel UID filter set to target UID 10001.

Benign Method

The independent trigger Pod contacted the AES-beta target through its ClusterIP Service and executed the normal encryption client. The client supplied an eight-byte key, submitted the plaintext SECURITY, retrieved the encrypted message and compared it with the locally calculated XOR result. Three runs were executed without automatic retry.

Preserved Anomaly

The first run waited for the non-protocol TCP connection used in Phase 5 to reach the target's approximately 900-second timeout. The target accepts one challenge session at a time, so this delayed the queued benign client. Once accepted, that benign target session completed in 6 ms and returned the expected result. The 138,181 ms client duration is therefore retained but is not interpreted as normal workload performance.

Evidence

Raw inputs are preserved under demo_project/k8s/minikube-ctf-cross-pod/evidence/cross-pod-20260817T052019Z/. Each benign-run-0N directory contains client output, target and monitor intervals, Pod state before and after the run, and run metadata. summary.tsv contains the aggregate machine-readable result, while commands.log records command provenance and the failed local audit wrapper.

Exploit Method

The exploit client recovered the stack canary by evaluating 1,792 candidates and then created one final worker that executed cat flag, for 1,793 workers per run. The application result was determined from flag recovery; detector success was established independently from the alert record.

Client-Validation Anomaly

The cross-Pod deployment generated an openECSC{...} flag, while the reused exploit client validated THESIS{...} by default. Runs 1 and 2 therefore returned status 1 despite flag recovery and detector success. The first configuration fix was itself malformed by Bash parameter expansion and is preserved. After moving the regex default into a literal assignment and testing it directly, run 3 returned status 0. No failed run was replaced.

Detector Evidence

Each alert contained, in order, shell execution, cat execution, resolved access to /opt/aes-beta/flag and a successful relative open of flag. All records carried UID 10001 and one shared host PID within the run. This supports detector completion for the target process tree; it does not establish cross-node or cluster-wide correlation.

Final Audit Status

The functional results were checked against the raw run directories, final cluster snapshot, effective manifests, cgroup records and command log. All planned benign, exploit, detector, loss-diagnostic and restart criteria are supported. Cross-node detection, least-privilege monitoring and production readiness remain NOT VERIFIED.
